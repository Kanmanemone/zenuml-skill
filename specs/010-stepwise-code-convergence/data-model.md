# Data Model: 정제 단계 코드 구체화

## 스코프 트리 정제 (2026-11-17, 아래의 모든 앞선 모델보다 우선)

- **TreeNode**(노드 원본 범위 안의 문장·인자·체인 고리, research S1)
  - `lines`: 자기 줄. 범위 기준 0부터의 줄 번호이며, 앞에 붙은 주석·어노테이션을 포함하고 자식의 줄은 뺀다.
  - `children`: 자식 TreeNode 목록(원본 순서). 비어 있으면 리프, 아니면 스코프다. 자식이 하나뿐인 층은 만들지 않는다(외길 병합).
  - `first`: 첫 코드 줄. 자리표시자의 들여쓰기와 형제 순서의 기준이다.
- **Root**: 루트 스코프. 선언 머리 줄(노드 자신의 주석·어노테이션·시그니처, 닫는 줄)과 자식들을 가진다.
- **Attached**(붙는 선언): 매개변수 하나, 또는 루트 영역의 코드 줄이 하나인 비공개 멤버·가변 상태 하나(앞의 주석·어노테이션 포함). `name`과 `lines`를 가지며, 트리 노드가 아니다. 코드 줄이 여럿인 비공개 멤버는 루트 자식 TreeNode다(research S9, 2026-11-18).
- **Scope 번호**: 노드마다 스코프를 후위 순서로 1부터 매긴다. 루트가 마지막이다. 스코프 목록과 `outline.json` 배열은 이 순서다.
- **`work/outline.json`**: `{"<node id>": [<스코프 항목>, …]}`
  - 스코프 항목은 `{"s": 목적 문장, "with": [자식 번호…], "sep": [{"ids": [자식 번호…], "s": 문장}, …]}`이다. 루트 항목에는 `s`·`with`가 없다. `sep`의 `s`는 그 묶음이 스코프 자식 하나뿐이면 생략할 수 있고, 그러면 그 자식의 `s`를 쓴다.
  - 검사: 모든 자식 번호가 `with`와 `sep`에 정확히 한 번씩 나온다. `sep`은 4개 이하다. 문장 규칙은 research S5를 따른다.
- **Step**(펼치기 단계, research S6)
  - `nodes`: `sep` 묶음 하나의 노드와 그 "함께 보임" 자손
  - `parent`: 그 묶음을 가진 스코프가 드러나는 단계(루트의 묶음이면 없음)
  - `number`: 단계 트리 전위 순서의 번호(1부터)
  - `title`: 묶음 문장
  - `attached`: 이름이 처음 쓰이는 붙는 선언
- **Scene**: 윤곽(0번째)과 단계마다 하나. 드러난 줄 = 루트 머리 + 1~k단계의 `nodes` 자기 줄 + 그 단계들의 `attached`다. 마지막 장면은 원본과 같다.
- 지우는 것: Node `units`, `outline.json`의 `placeholders`·`folds`.

## 단위 펼치기 (아래의 모든 앞선 모델보다 우선)

- Stage `kind`: `prose`(첫 장면) · `outline` · `unfold`(노드별 단위 수만큼 반복) · `source`(마지막). 반복 필드 `repeat`와 의존 반복은 없앤다.
- Node `units`: 단위 목록. 단위마다 `names`(드러나는 멤버·문장 이름), `lines`(범위 기준 1부터의 줄 번호 — 멤버, 붙은 비공개 멤버·상태, 매개변수, 그 주석)를 담는다. 구체화하지 않는 노드는 빈 목록이다.
- Node `responsibility`: 책임 한 줄(그대로).
- `work/outline.json`: `{"<node id>": {"placeholders": [문장, …], "folds": [{"from": n, "to": m, "text": 문장}, …]}}`. 메인 에이전트가 쓰는 유일한 코드 장면 입력이다.
- 작업 파일은 `work/01/<id>.kt`(상황 문단)과 `work/original/<id>.kt`(원본 범위)만 남는다.


## 2026-11-16 변경 (아래 초기 모델보다 우선)

Stage: `kind`(`prose`/`code`, 기본 code), `repeat`(`dependency` 또는 없음). 반복 확장본: `template`(기본 별명), `targets`(노드 ID → 상대·관계 라벨), `occurrence`(1부터). Node: `dependencies`(중복 없는 직접 상대·라벨 순서). 표시 목록·번호는 노드별로 계산한다. prose도 내부 파일은 `.kt`지만 코드로 해석하지 않는다. 원본 없는 노드도 원본과 무관한 앞 장면은 생성한다.

데이터베이스는 없다. 아래는 `stages.py`가 다루는 데이터와 파일이다. 파일 형식의 세부는 [contracts/stages-contract.md](contracts/stages-contract.md)에 있다.

## Stage (정제 단계) — `stages.md`에서 읽음

| 필드 | 설명 | 규칙 |
|---|---|---|
| `index` | 1부터 시작하는 번호 | 정의에 적힌 순서에서 나온다. 파일에는 적지 않는다. |
| `visible` | 이번 실행에서 보일지 | 설정 `stages`와 요청 옵션에서 정한다. 마지막 단계는 항상 `true`다(FR-009a). |
| `work` | 작업 폴더 번호 | 만드는 단계끼리 1부터 매긴다. 첫 단계가 아닌 끈 단계는 만들지 않으므로 번호가 없다(research R13). |
| `display` / `of` | 화면 번호와 보이는 단계 수 | 보이는 단계끼리 1부터 매긴다. |
| `merged` | 이 단계에 합쳐진 끈 단계들의 `becomes`·`notation` | 첫 단계가 아닌 끈 단계의 몫을 다음에 만드는 단계가 받는다. |
| `nickname` | 별명 | 비어 있지 않고, 정의 안에서 겹치지 않는다. |
| `becomes` | 이 단계에서 원본과 같아지는 것 | 필수. 모델만 읽는다. |
| `unrevealed` | 아직 드러나지 않은 것 | 필수. 모델만 읽는다. |
| `notation` | 보조 표기 규칙 | 선택. 모델만 읽는다. |

- 단계는 2개 이상이어야 한다. 첫 단계와 마지막 단계는 자리로 역할이 정해진다. 첫 단계는 지어낸 코드(FR-003~005)이고, 마지막 단계는 원본 범위의 복사(FR-010)다.
- 화면 제목은 `<display>단계: <nickname> (<display>/<of>)` 형식이다.

## Node (노드) — 구조 뷰에서 읽음

| 필드 | 설명 |
|---|---|
| `id` | Mermaid 노드 Id. 작업 파일 이름으로도 쓴다. |
| `name` | 선언·파일 연결용 이름. 라벨에서 변경 표시 이모지와 인라인 태그를 뺀 뒤 마지막 `&nbsp;` 뒤 토큰을 쓴다(003 FR-036 규격 표시어 제외). `&nbsp;`가 없으면 정리한 전체 라벨이며 모든 단계에서 바뀌지 않는다. |
| `order` | 선언 순서 |
| `group_path` | 소속 subgraph들의 `(Id, 라벨)` 목록. 최상위부터 적고, 그룹이 없으면 빈 목록이다. |
| `link` | `click` 대상 문자열. 없으면 null이다. |
| `range` | 원본 범위(R5, S10). `{source, start_line, end_line}` 형태이고, 파일 단위 노드는 `whole_file: true`가 더해진다(시작 1, 끝은 파일의 마지막 줄). 구체화하지 않는 노드는 null이다. |
| `candidates` | 같은 이름의 선언이 여럿일 때의 후보 `{pick, start_line, end_line, header}` 목록. 하나뿐이면 빈 목록 |
| `pick` | 모델이 고른 후보 번호(1부터). `prepare --pick`으로 받는다(spec FR-002) |
| `responsibility` | 구조 뷰 `#### 요소의 책임`에서 그 노드 항목의 `책임 (추상)` 문장. 없거나 `설명에 명시되지 않음`으로 시작하면 null이다(spec FR-015e). |
| `skip_reason` | 구체화하지 않는 이유 한 줄. 구체화하는 노드는 null이다(FR-017). |
| `doc` | 들어갈 문서 이름 |

- 노드 하나가 상자 하나다. 같은 파일의 여러 노드, 중첩 노드도 각자 상자를 갖는다.
- 상자의 순서는 문서 안에서 노드를 선언한 순서다.

## Document (문서) — FR-015c

| 필드 | 설명 |
|---|---|
| `name` | `<subgraph Id>.md`, `others.md`, `all.md` 중 하나 |
| `title` | 최상위 그룹 라벨, `기타`, 또는 구조 뷰 slug |
| `nodes` | 들어갈 노드들(순서대로). 하위 그룹이나 작은 그룹의 라벨로 묶어 보인다. |

나누는 규칙은 아래 순서로 적용한다.

1. 전체 노드가 5개 이하이거나 subgraph가 없으면 `all.md` 하나만 만든다.
2. 그렇지 않으면 노드가 3개 이상인 최상위 그룹마다 `<Id>.md`를 하나씩 만든다. 하위 그룹의 노드도 개수에 넣는다.
3. 노드가 2개 이하인 최상위 그룹과 그룹에 속하지 않은 노드는 `others.md` 하나에 모은다. 해당하는 노드가 없으면 `others.md`는 만들지 않는다.

## Stage code (단계 코드) — 작업 파일

`g`는 이번 실행에서 만드는 단계 수다(끈 단계를 뺀 수, research R13). 번호는 작업 폴더 번호(`work`)다.

| 단계 | 파일 | 쓰는 주체 |
|---|---|---|
| 1 | `work/01/<node id>.kt` | 1단계 서브에이전트(R1) |
| 2 … g-1 | `work/<NN>/<node id>.kt` (구체화하는 노드만) | `begin`이 복사하고, 메인 에이전트가 적은 `work/edits.txt`를 `apply`가 적용한다(R11). |
| g (마지막) | 없음. `work/original/<node id>.kt`를 그대로 쓴다. | `prepare`가 원본 범위를 잘라 둔다. |

## 상태 흐름

```text
prepare ─▶ (서브에이전트) work/01 ─▶ begin 2 ─▶ apply 2 ─▶ begin 3 ─▶ apply 3 … begin g-1 ─▶ apply g-1 ─▶ build
```

- `begin k`는 `work/<k-1>`과 그 작업 파일이 모두 있어야 하고, `work/<k>`가 이미 있으면 거부한다. 지나간 단계를 되돌아가 덮어쓰지 않기 위해서다.
- `build`는 1단계와 2…g-1단계의 작업 파일이 모두 있어야 한다.
- 어느 노드의 k단계 코드가 k-1단계와 같으면, 그 단계에 "이 단계에서는 달라진 것이 없음"이 붙는다(FR-014).

## 2026-11-23 변화 0단계

- **비교 기준** (`manifest.compare`): `base`(짧은 해시), `head`(짧은 해시 또는 null = 작업 트리). `prepare --base`가 있을 때만 있다.
- **노드 변화** (`node.change`): `changed` | `removed` | `added` | `same` | null. 변경 전·후 원본 범위(R16)로 정해지며 구조 뷰 표시와 무관하다. `removed`이면 `original`이 변경 전 범위를 가리킨다. `changed`이면 `work/before/<id>.kt`가 있다.
- **0단계 줄** (`changed` 노드 build 때만, 저장하지 않음): `(줄, add|mod|del|None)`의 목록이다. 불변식: `del`을 빼면 `work/original/<id>.kt`, `add`·`mod`를 빼면 `work/before/<id>.kt`와 글자까지 같다.

## 2026-11-24 -1단계

- **-1단계 장면** (`changed` 노드이고 `stages.md`에 `before` 단계가 있을 때, build 때만, 저장하지 않음): 코드는 `work/before/<id>.kt`와 글자까지 같고 줄 클래스가 없다. 0단계가 없는 노드에는 없다.

## 2026-11-24 노드 제목의 변화 표시와 링크

- 새 필드는 없다. 노드 제목은 manifest의 `change`(이모지)와 `link`(href)로, 머리말은 `compare`로 build 때 정해진다.

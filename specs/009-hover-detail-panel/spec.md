# Feature Specification: 다이어그램 노드 hover로 책임·협력 보기

**Feature Branch**: `009-hover-detail-panel`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "generating-architecture-views 구조 뷰에서 다이어그램 노드에 마우스를 올리면(hover) 그 노드의 Responsibility와 Collaboration을 그 자리에서 볼 수 있게 한다. 지금은 노드 하나를 이해하려고 다이어그램과 Responsibility·Collaboration 섹션 사이를 스크롤로 오가며 시선을 계속 전환해야 해서 피로도가 크다(문서 내 앵커 하이퍼링크 이동은 시도했지만 잘 작동하지 않았다). 결정된 방향: (1) Mermaid `click` 지시어의 툴팁 자리에 내용을 넣는다 — 툴팁은 고정 문자열만 받으므로 내용은 복사본이다. (2) 원본은 본문(Responsibility·Collaboration)이고, 스킬과 함께 제공하는 스크립트가 본문을 읽어 같은 산출 파일의 `click` 툴팁을 채운다(같은 파일 덮어쓰기, 여러 번 돌려도 결과 같음, 본문을 고친 뒤 따로 다시 실행해 툴팁을 갱신할 수 있음). 모델이 툴팁을 직접 쓰지 않으므로 토큰 영향 없음. (3) 툴팁 기본 모양은 폭 200px라 좁으므로, 산출 md 맨 위에 고정 `<style>` 블록을 넣어 툴팁을 미리보기 아래쪽에 가로로 넓게 고정된 상세 패널(높이 최대 45vh, 왼쪽 정렬)로 바꾼다 — 별도 CSS 파일이나 VS Code 설정 없이 md 하나로 동작해야 한다. 오른쪽 위 고정은 hover 중인 노드를 가려서 버렸다. (4) 대상 환경은 VS Code Markdown 미리보기다. GitHub는 `<style>`과 다이어그램 상호작용을 막으므로 hover를 지원하지 않으며, GitHub에서는 문서가 깨지지 않기만 하면 된다(`<style>` 내용이 본문에 글자로 드러나지 않아야 함 — 미확인). VS Code 미리보기에서 Mermaid 툴팁이 뜨는지와 md 안 `<style>`이 적용되는지도 아직 미확인이며 docs/hover-tooltip-test/ 테스트 키트로 확인 예정. (5) 설정: 기존 settings.jsonc의 responsibility·collaboration 아래에 `hover` 키를 추가한다. responsibility.hover: off / summary(책임 (추상) 한 줄) / full(책임 (추상) + 역할 (구체)), 기본 full. collaboration.hover: off / targets(그 노드가 관여한 협력의 대상과 방향만, 예: → PaymentService (호출)) / full(대상·방향 + 책임의 경계, 분리 이유 & 합리성 평가, 내가 할 수 있는 질문), 기본 targets. display가 hidden이면 hover 값과 상관없이 off로 동작한다. 토큰 영향은 모두 "토큰 소모 영향 없음". (6) 제약: 툴팁 텍스트 안에 큰따옴표 불가, 툴팁은 노드에만 뜨고 엣지에는 안 뜨므로 Collaboration은 노드 기준(→/← 대상)으로 풀어 넣는다, 툴팁은 `click`에 링크가 있어야만 달 수 있으므로 링크 대상이 없는 노드는 hover가 없다(가짜 링크 금지), 패널은 스크롤 불가. (7) 기존 spec 영향: 003의 AP-13c "내용만" 허용 목록에 파일 맨 위 고정 `<style>` 블록을 추가하고, 003의 `click` 툴팁 규칙(지금은 파일 이름)을 hover가 켜지면 내용으로 바뀌도록 고친다. 007 설정 정의(settings.schema.json 포함)에 두 옵션을 추가한다 — 007이 003 규칙에 예외를 추가한 것과 같은 방식으로 기록한다."

## Clarifications

### Session 2026-11-14

- Q: GitHub에서 md 안 `<style>`이 글자로 드러나는데, 패널 CSS를 어디에 둘 것인가? → A: GitHub 지원을 깔끔하게 포기하고 VS Code Markdown 미리보기에만 집중한다. md 안 `<style>` 블록(FR-005)을 그대로 쓰고, GitHub에서의 모양(CSS 글자 노출 포함)은 요구 사항에서 뺀다.
- Q: `<style>` 블록을 문서 맨 위 대신 맨 아래에 두어도 되는가? → A: 맨 아래에 둔다. VS Code 미리보기에서는 위치와 상관없이 문서 전체에 적용되어 동작이 같고, 원문을 열면 본문이 바로 시작된다.
- Q: 링크가 없는 노드도 hover 중임을 알 수 있어야 하는가? → A: 그렇다. 패널 내용이 있는 모든 노드(링크 유무와 무관)는 마우스를 올린 동안 노드 이름에 밑줄이 생긴다. FR-005 블록에 규칙으로 넣는다.
- Q: 패널을 미리보기 아래에 고정할지 노드 바로 아래에 띄울지를 사용자가 고를 수 있어야 하는가? 노드 아래일 때 모양은? → A: `hover.position` 설정으로 고른다. `bottom`(미리보기 아래 고정 패널, 기본값) / `node`(Mermaid 기본 위치인 노드 아래). `node`는 Mermaid 기본 모양을 따르되 왼쪽 정렬로 바꾸고 최대 폭을 `25em`(글자 크기 12px에서 약 300px, 한글 한 줄 약 25자)으로 둔다. 200px·25em·33em 세 폭을 VS Code에서 비교해 정했다. 오른쪽 끝 노드에서 툴팁이 남은 공간만큼 좁아지는 문제는, 툴팁을 늘 같은 폭으로 펴고 오른쪽으로 넘칠 때만 미리보기 오른쪽 끝에 붙이는 방식으로 해결한다(VS Code에서 확인). GitHub에서는 이 방식도 동작하지 않음을 확인했다(범위 밖).
- Q: hover 설정을 각 섹션(`responsibility`·`collaboration`·`dependency`) 아래에 나눠 둘 것인가, 한 곳에 모을 것인가? → A: 사용자는 "hover 창을 손보자"로 설정 파일을 연다. 설정 최상위에 `hover` 그룹을 두고 `hover.responsibility`, `hover.collaboration`, `hover.position` 세 키로 모은다(이전 이름: `responsibility.hover`, `collaboration.hover`, `dependency.hoverPosition`). `display`가 `hidden`이면 그 섹션의 hover 값이 `off`로 동작한다는 규칙은 그대로이며, 두 값이 떨어져 있으므로 설정 파일 주석에 적는다.
- (사용자 결정) `bottom` 패널의 높이 상한(미리보기 높이의 45%)을 없앤다. 내용이 많으면 패널이 다이어그램을 가릴 수 있지만, 내용이 잘리는 쪽이 더 나쁘다고 보았다. 패널은 내용만큼 위로 늘어나며, 미리보기 화면 높이만 넘지 않는다(넘으면 화면 위로 밀려나 패널 첫 줄부터 보이지 않게 되므로).
- (사용자 결정) `bottom` 패널은 내용을 폭 `25em`짜리 칸 여러 개에 나눠 흘린다(다단). 패널이 미리보기 폭 전체를 쓰므로, 칸 수는 미리보기 폭에 따라 자동으로 정해진다(14px 글자 기준 미리보기 폭 약 750px 이상에서 2칸). 같은 내용의 패널 높이가 칸 수만큼 줄어 다이어그램을 덜 가리고 잘리는 일도 줄어든다. 칸 폭은 `node` 모드의 툴팁 폭과 같은 한 줄 글자 수 기준을 따른다.
- (사용자 결정) 패널의 Collaboration 부분에는 그 노드가 의존하는 협력과 서로 의존하는 협력만 넣고, 그 노드에 의존하는 쪽(의존받음)은 넣지 않는다. 본문 Collaboration도 "X는 Y에 의존한다" 한 방향으로만 쓰며 "Y는 X의 의존 대상이다" 같은 역방향 표현을 쓰지 않기 때문이다. 따라서 다른 노드에 의존하지 않는 노드의 패널에는 Collaboration 부분이 없다.
- (사용자 결정) 패널의 협력 머리줄은 화살표 대신 본문 Collaboration 첫 줄에서 주어(그 노드)만 뺀 문장으로 쓴다 — 본문 "<strong>X</strong>는 <strong>Y</strong>에 의존한다."는 X의 패널에서 `Y에 의존한다 (관계)`, "X와 Y는 서로 의존한다."는 `Y와 서로 의존한다 (관계)`가 된다.
- (사용자 결정) 패널 맨 윗줄에 그 노드의 이름을 굵게 표시해, 지금 어느 노드의 내용을 보는지 바로 알 수 있게 한다.
- (사용자 결정) 패널에서 세부 분석의 하위 항목은 글머리 목록 대신 한 문단으로 이어 붙인다(예: `**책임의 경계**: View는 상태를 그리고 입력을 모은다. ViewModel은 상태를 계산하고 이벤트를 처리한다. 경계는 uiState 구독과 이벤트 함수 호출이다.` — 제목은 굵게, 같은 줄에 콜론으로 이어 쓴다).
- (사용자 결정) `hover.enabled`(`true`/`false`, 기본값 `true`) 하나로 hover 기능 전체를 켜고 끈다. `false`이면 `hover.responsibility`·`hover.collaboration` 값과 상관없이 두 목록이 모두 빈 것처럼 동작하므로, 항목 설정을 건드리지 않고 기능만 끄고 다시 켤 수 있다.
- (사용자 결정) hover 항목 설정을 단계 값(`off`/`summary`/`full`, `off`/`targets`/`full`)에서 항목 목록으로 바꿔, 넣을 항목과 순서를 하나하나 고를 수 있게 한다. `hover.responsibility`는 `abstract`·`concrete`, `hover.collaboration`은 `targets`·`boundary`·`rationale`·`questions` 중에서 고른다. `hover.collaboration` 기본값은 `["targets", "boundary", "rationale"]`(질문 제외)다. 패널 안에서 Responsibility는 항상 Collaboration 위이며, 모르는 항목이나 중복 항목은 잘못된 값으로 본다.

### Session 2026-11-15

- (사용자 결정) `bottom` 패널의 다단은 내용이 3줄을 넘을 때(미리보기에 보이는 줄 기준, 4줄부터)만 쓴다. 3줄짜리 내용이 칸마다 한 줄씩 나뉘면 오히려 읽기 어렵기 때문이다. 그래서 칸 하나의 높이는 최소 3줄이다 — 3줄 이하는 한 칸에 모두 들어가고, 4줄은 2줄+2줄, 6줄은 3줄+3줄로 나뉜다. 그 대가로 1~2줄짜리 패널도 높이는 3줄이 된다(미리보기의 칸 나누기가 "칸마다 최소 줄 수"를 직접 지정하는 방법을 따르지 않음을 Chrome 157에서 확인했다).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 노드에 마우스를 올려 책임과 협력을 그 자리에서 보기 (Priority: P1)

사용자가 구조 뷰 파일을 VS Code Markdown 미리보기로 열고 Dependency 다이어그램의 노드에 마우스를 올리면, 미리보기 아래쪽에 가로로 넓은 상세 패널이 뜨고 그 노드의 Responsibility와 그 노드가 의존하는 Collaboration이 보인다. 마우스를 떼면 패널이 사라진다. 다이어그램에서 시선을 떼고 본문으로 스크롤할 필요가 없다.

**Why this priority**: 사용자가 해결하려는 핵심 문제(다이어그램과 본문 사이를 스크롤로 오가며 생기는 시선 전환 피로)를 직접 해결한다.

**Independent Test**: 링크가 붙은 노드가 여러 개인 구조 뷰를 VS Code 미리보기로 열어, 각 노드에 마우스를 올렸을 때 패널에 그 노드의 본문 내용이 뜨는지, 내용이 미리보기 높이를 넘지 않는 한 패널 내용이 잘리지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기본 설정으로 만든 구조 뷰, **When** 사용자가 링크가 붙은 노드에 마우스를 올리면, **Then** 미리보기 아래쪽에 왼쪽 정렬된 넓은 패널이 뜨고, 그 노드의 책임 (추상)·역할 (구체)와 그 노드가 의존하는 협력의 대상·관계(예: `PaymentService에 의존한다 (호출)`)가 보인다. 그 노드에 의존하는 쪽은 보이지 않는다.
2. **Given** 같은 구조 뷰(`hover.position`이 기본값 `bottom`), **When** 다이어그램의 오른쪽 아래 끝에 있는 노드에 마우스를 올리면, **Then** 패널이 다른 노드와 같은 위치(미리보기 아래쪽)에 뜨고, 내용이 미리보기 화면 높이 안에 들어가는 한 오른쪽이나 아래쪽 경계에서 잘리지 않는다.
3. **Given** 본문에서 굵게·코드로 표시된 이름이 있는 항목, **When** 패널이 뜨면, **Then** 굵게·코드 표시가 패널에서도 구분되어 보인다.
4. **Given** 링크 대상이 없는 노드, **When** 그 노드에 마우스를 올리면, **Then** 링크가 있는 노드와 같은 패널이 뜨고 노드 이름에 밑줄이 생기며, 그 노드를 클릭해도 어디로도 이동하지 않는다.
5. **Given** 구조 뷰 파일, **When** 같은 파일을 PNG나 PDF로 내보내면, **Then** 패널 모양을 정하는 블록의 내용이 결과에 글자로 드러나지 않는다.
6. **Given** 링크가 있는 노드와 없는 노드가 섞인 구조 뷰, **When** 각 노드에 마우스를 올렸다 떼면, **Then** 올린 동안에만 그 노드 이름에 밑줄이 생기고, 밑줄 모양은 링크 유무와 상관없이 같다.

### User Story 2 - hover 패널에 넣을 양을 설정으로 고르기 (Priority: P2)

사용자는 스킬 설정 파일의 `hover` 그룹 한 곳에서 hover 패널에 넣을 양을 섹션별로 고른다. Responsibility는 책임 (추상)·역할 (구체) 중에서, Collaboration은 대상·관계 줄, 책임의 경계, 분리 이유 & 합리성 평가, 내가 할 수 있는 질문 중에서 넣을 항목과 순서를 목록으로 고른다. `hover.enabled` 하나로 기능 전체를 끄고 켤 수도 있다. 본문 표시 방식(`display`)과는 따로 정한다. 같은 그룹에서 패널을 미리보기 아래에 고정할지 노드 바로 아래에 띄울지도 고른다.

**Why this priority**: 패널은 스크롤이 안 되고 미리보기 화면보다 커질 수 없으며, 내용이 많을수록 다이어그램을 많이 가리므로, 노드가 많이 연결된 구조에서는 넣는 양을 줄일 수 있어야 실제로 쓸 수 있다. 다만 P1의 기본값만으로도 기능의 가치는 전달된다.

**Independent Test**: 같은 설명으로 hover 설정 조합을 바꿔 가며 구조 뷰를 만들어, 패널 내용이 설정 값대로 달라지는지와 본문은 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** `hover.responsibility`가 `["abstract"]`, **When** 노드에 마우스를 올리면, **Then** 패널에 책임 (추상) 한 줄만 있고 역할 (구체)는 없다.
2. **Given** `hover.responsibility`가 `["concrete", "abstract"]`, **When** 노드에 마우스를 올리면, **Then** 패널에 역할 (구체)가 책임 (추상)보다 먼저 나온다.
3. **Given** `hover.collaboration`이 `["targets", "boundary", "rationale", "questions"]`, **When** 노드에 마우스를 올리면, **Then** 패널에 그 노드가 의존하는 협력마다 대상·관계 줄과 함께 책임의 경계, 분리 이유 & 합리성 평가, 내가 할 수 있는 질문이 있다.
4. **Given** `hover.collaboration`이 `["questions"]`(대상 줄 `targets`를 적지 않음), **When** 노드에 마우스를 올리면, **Then** 어느 협력의 질문인지 알 수 있도록 협력마다 대상·관계 줄이 붙고 그 아래에 질문만 있다.
5. **Given** 두 hover 목록(`hover.responsibility`·`hover.collaboration`)이 모두 `[]`, **When** 구조 뷰를 만들면, **Then** 산출 파일은 이 기능 도입 전과 같다(툴팁은 파일 이름, 패널 모양을 정하는 블록 없음).
6. **Given** `responsibility.display`가 `hidden`이고 `hover.responsibility`가 `["abstract", "concrete"]`, **When** 구조 뷰를 만들면, **Then** 패널에 Responsibility 내용이 들어가지 않는다(빈 목록으로 동작).
7. **Given** 설정과 다른 hover 양을 요청 문장에서 직접 밝힌 경우, **When** 구조 뷰를 만들면, **Then** 그 요청에 한해 요청 값이 설정보다 우선한다.
8. **Given** `hover.position`이 `node`, **When** 노드에 마우스를 올리면, **Then** 그 노드 바로 아래에 왼쪽 정렬된 툴팁이 뜨고, 한 줄이 약 25em(한글 약 25자)을 넘으면 줄이 바뀐다. 툴팁 배경·테두리는 Mermaid 기본 모양이다.
9. **Given** `hover.position`이 `node`, **When** 오른쪽 끝 노드에 마우스를 올린 뒤 왼쪽 끝 노드에 마우스를 올리면, **Then** 오른쪽 끝 노드의 툴팁은 미리보기 오른쪽 끝에 붙어 잘리지 않고, 왼쪽 끝 노드의 툴팁은 그 노드 아래에 뜨며, 두 툴팁의 폭이 같다.
10. **Given** `hover.position`만 `bottom`에서 `node`로 바꾼 경우, **When** 기존 파일에 도구를 다시 실행하면, **Then** 패널 모양 블록만 바뀌고 툴팁 내용과 본문은 그대로다.
11. **Given** `hover.responsibility`·`hover.collaboration`이 기본값이고 `hover.enabled`가 `false`, **When** 구조 뷰를 만들면, **Then** 산출 파일은 이 기능 도입 전과 같다. **When** `hover.enabled`만 `true`로 바꾸고 다시 만들면, **Then** 패널에 책임·역할과 의존 대상(책임의 경계, 분리 이유 & 합리성 평가 포함)이 들어간다.

### User Story 3 - 본문을 고친 뒤 패널 내용 다시 맞추기 (Priority: P3)

사용자가 이미 만들어진 구조 뷰 파일의 Responsibility나 Collaboration 본문을 직접 고친 뒤, 스킬과 함께 제공되는 도구를 그 파일에 다시 실행하면 패널 내용이 고친 본문에 맞춰진다. 모델에게 구조 뷰를 다시 만들어 달라고 할 필요가 없다.

**Why this priority**: 패널 내용은 본문의 복사본이라 본문만 고치면 둘이 어긋난다. 다시 맞추는 방법이 없으면 복사본이 옛 내용을 보여주게 되지만, 생성 직후에는 둘이 항상 일치하므로 P1·P2보다 뒤에 둔다.

**Independent Test**: 구조 뷰를 만든 뒤 본문의 한 문장을 고치고 도구를 실행해, 패널에 고친 문장이 나오는지와 도구를 한 번 더 실행해도 파일이 바뀌지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 본문의 한 요소 책임 문장을 고친 구조 뷰 파일, **When** 사용자가 그 파일에 도구를 실행하면, **Then** 그 요소의 패널 내용이 고친 문장으로 바뀌고 다른 부분은 바뀌지 않는다.
2. **Given** 방금 도구를 실행한 파일, **When** 도구를 한 번 더 실행하면, **Then** 파일 내용이 바이트 단위로 같다.
3. **Given** 이 기능 도입 전에 만든 구조 뷰 파일, **When** 사용자가 그 파일에 도구를 실행하면, **Then** 패널 내용과 패널 모양을 정하는 블록이 추가되고 본문은 바뀌지 않는다.
4. **Given** 설정에서 두 hover 목록을 모두 `[]`로 바꾸거나 `hover.enabled`를 `false`로 바꾼 뒤, **When** 기존 파일에 도구를 실행하면, **Then** 툴팁이 파일 이름으로 돌아가고 패널 모양을 정하는 블록이 사라진다.

### Edge Cases

- **본문에 큰따옴표가 있는 경우**: 툴팁 문자열 안에는 큰따옴표를 쓸 수 없으므로, 패널 내용에서는 다이어그램 문법을 깨뜨리지 않는 다른 표기로 바꿔 넣는다. 본문은 바꾸지 않는다.
- **병렬 형제 요소를 하나로 묶은 Responsibility 항목**(003의 parallel-sibling consolidation): 묶인 각 요소의 패널에 그 묶인 항목 전체를 넣는다 — 항목 안에서 요소별 근거를 잘라내지 않는다.
- **여러 대상을 하나로 묶은 Collaboration 항목**(003의 multi-target consolidation): 출발 노드의 패널에만 묶음 이름(예: `feature 내비게이션 요소들에 의존한다 (호출)`)으로 넣는다. 묶인 각 대상 노드의 패널에는 이 협력을 넣지 않는다(의존받는 쪽이므로).
- **그룹 수준 항목**: 그룹(subgraph)에는 hover가 없으므로 그룹의 책임과 그룹 간 비교는 패널에 넣지 않는다.
- **서로 의존하는 쌍**: 양쪽 노드 패널 모두에 `상대와 서로 의존한다 (관계)`로 표시한다. 괄호 안 관계는 그 패널 주인 노드에서 상대로 가는 엣지의 라벨이다(두 방향 라벨이 달라도 각자 자기 쪽 라벨).
- **본문에 해당 노드 항목이 없는 경우**(예: 본문을 사람이 지운 경우): 그 노드의 패널에서 해당 섹션 내용은 비우고, 두 섹션 모두 비면 툴팁을 파일 이름으로 돌린다.
- **내용이 적은 경우**(`bottom`): 내용이 3줄 이하이면 칸을 나누지 않고 한 칸에만 흐른다. 1~2줄이어도 패널 높이는 3줄이다.
- **내용이 많은 경우**(`bottom`): 내용은 먼저 여러 칸(칸마다 최소 3줄 높이)으로 나뉘어 흐르고, 그래도 많으면 패널이 내용만큼 위로 늘어나 다이어그램을 가릴 수 있다. 미리보기 폭이 좁으면 칸이 하나뿐이라 높이가 그만큼 커진다. 미리보기 화면 높이를 넘는 부분만 잘리며, 스크롤은 되지 않는다. 설정으로 넣는 양을 줄여 대응한다.
- **오른쪽 끝 근처 노드**(`node`): 툴팁을 노드 아래에 띄우면 미리보기 오른쪽으로 넘치는 경우, 같은 폭을 유지한 채 미리보기 오른쪽 끝에 붙여 띄운다(세로 위치는 그대로). 툴팁은 좁아지지도 잘리지도 않는다. 다음에 다른 노드에 마우스를 올리면 다시 노드 아래 위치부터 판단한다.
- **문서 맨 끝 근처의 다이어그램**(`node`): 툴팁이 문서 아래 끝을 넘으면 오른쪽 끝에 붙이는 판단이 동작하지 않아 툴팁이 잘릴 수 있다. 구조 뷰는 다이어그램 아래에 본문이 이어지므로 실제로는 드물다. 보정하지 않는다.
- **화면 아래 끝 근처 노드**(`node`): 툴팁이 미리보기 화면 아래로 넘치면 넘친 부분은 보이지 않는다. 보정하지 않으며, 긴 내용은 `bottom` 모드를 쓰거나 항목을 줄여 대응한다. CSS로는 고칠 수 없음을 확인했다 — 툴팁은 문서 기준으로 위치가 정해지는데, 화면 끝을 알려 줄 화면 고정 요소는 CSS 규칙상 툴팁의 앵커가 될 수 없다(Chrome 157에서 확인).
- **링크 대상이 없는 노드**(003 하이퍼링크 해석 결과 "링크 없음"): 링크 대신 이동하지 않는 형태로 툴팁만 단다(FR-013). 설명에 파일 경로·URL이 전혀 없어도 모든 노드에 패널이 뜬다. 이런 노드는 마우스 커서가 일반 모양 그대로이고, hover 중 밑줄만 생긴다(FR-005·FR-013).
- **Markdown 링크가 들어 있는 본문**(예: `<strong>[이름](경로)</strong>`): 패널에는 링크 없이 이름 글자만 넣는다(패널은 클릭할 수 없다).
- **구조 변화(동적) 요청의 CRUD 라벨**: 노드 라벨의 ✨/♻️/🗑️ 접두는 패널 내용에 영향을 주지 않는다. 본문 항목을 노드에 대응시키는 데에는 노드 이름을 쓴다.
- **도구를 실행할 Python이 없는 환경**: Python 3.9 이상을 찾지 못하면 도구를 실행하지 않는다. 구조 뷰는 이 기능 도입 전 형태(툴팁은 파일 이름)로 저장되고, 채팅 응답 끝에 hover를 건너뛰었다는 안내 한 줄만 남는다. 구조 뷰 생성 자체는 실패로 보지 않는다.
- **PNG/PDF 내보내기**: 패널은 마우스를 올렸을 때만 뜨므로 내보낸 결과에는 보이지 않으며, 패널 모양을 정하는 블록이 내보낸 결과에 글자로 드러나서도 안 된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `hover.enabled`가 `true`이고 `hover.responsibility`나 `hover.collaboration` 중 하나라도 빈 목록이 아니면(그리고 해당 섹션의 `display`가 `hidden`이 아니면), 스킬은 구조 뷰 파일과 피드백 로그를 저장한 뒤 함께 제공되는 도구(`scripts/apply_hover.py`)를 실행해 각 노드의 툴팁을 그 노드의 패널 내용으로 채워야 한다. 모델은 툴팁 내용을 직접 쓰지 않는다.
- **FR-002**: 패널 내용의 유일한 원본은 같은 파일의 Responsibility·Collaboration 본문이어야 한다. 도구는 본문을 읽어 패널 내용을 만들고 본문 자체는 바꾸지 않는다.
- **FR-003**: 도구는 같은 파일을 덮어써야 하며, 같은 파일과 같은 설정으로 여러 번 실행해도 결과가 같아야 한다(멱등).
- **FR-004**: 도구는 스킬 실행과 별개로, 사용자가 기존 구조 뷰 파일 하나를 지정해 직접 실행할 수 있어야 한다. 이때 hover 양과 패널 위치는 설정 파일 값을 따른다.
- **FR-005**: 패널이 들어간 파일은 맨 아래(본문의 마지막 내용 다음)에 패널 모양을 정하는 고정 블록(`<style>`) 하나를 가져야 한다. 블록 내용은 `hover.position`(FR-019) 값마다 고정이며 요청마다 달라지지 않는다. `bottom`이면 툴팁을 미리보기 아래쪽에 좌우로 넓게 고정되고, 왼쪽 정렬이며, 높이에 별도 상한이 없는 패널로 바꾼다(내용만큼 늘어나되 미리보기 화면 높이는 넘지 않는다). 패널 안의 내용은 폭 `25em`짜리 칸에 나눠 흘리며, 칸 수는 미리보기 폭에 따라 정해진다. 다만 칸 하나의 높이는 최소 3줄이어서, 내용이 3줄 이하이면 한 칸에만 흐르고 4줄부터 여러 칸으로 나뉜다(1~2줄짜리 패널도 높이는 3줄). `node`이면 툴팁 배경·테두리와 기본 위치(노드 아래)는 Mermaid대로 두고, 왼쪽 정렬로 바꾸며, 폭을 남은 공간과 상관없이 내용 폭(최대 `25em`)으로 두고, 미리보기 오른쪽으로 넘칠 때만 오른쪽 끝에 붙인다. 이를 위해 넘침 판단 기준을 문서 전체로 두고, hover 중인 노드가 없을 때는 툴팁을 화면에서 빼서 직전 노드에서 쓴 위치가 다음 노드에 이어지지 않게 한다(이 때문에 `node`에서는 마우스를 떼면 툴팁이 흐려지는 효과 없이 바로 사라진다). 블록은 이 동작에 필요한 최소한의 속성만 담는다. 여기에 더해, 패널 내용이 있는 노드(링크 유무와 무관)에 마우스를 올린 동안 노드 이름에 밑줄을 긋는 규칙 하나를 담는다. 이 밑줄은 "지금 이 노드를 hover하고 있다"는 표시다.
- **FR-006**: 패널 내용이 들어간 노드가 하나도 없으면(`hover.enabled`가 `false`이거나, 두 hover 목록이 모두 비었거나, 본문에 대응하는 항목이 없는 경우) 파일에는 FR-005 블록도, 링크 없는 노드용 툴팁 줄(FR-013)도 없어야 하고, 링크가 있는 노드의 `click` 툴팁은 기존 규칙(파일 이름)대로여야 한다. 도구는 이 상태로 되돌리는 일도 해야 한다.
- **FR-007**: 별도 CSS 파일이나 편집기 설정 없이 산출 md 파일 하나만으로 VS Code Markdown 미리보기에서 패널이 동작해야 한다.
- **FR-008**: `hover.responsibility` 값은 패널에 넣을 항목의 목록이다. 항목은 `abstract`(책임 (추상))와 `concrete`(역할 (구체))이며, 적은 항목만 적은 순서대로 넣는다. `[]`이면 Responsibility 부분을 넣지 않는다. 기본값은 `["abstract", "concrete"]`다.
- **FR-009**: `hover.collaboration` 값은 그 노드가 의존하는 협력마다 넣을 항목의 목록이다. 항목은 `targets`(대상·관계 줄), `boundary`(책임의 경계), `rationale`(분리 이유 & 합리성 평가), `questions`(내가 할 수 있는 질문)이며, 적은 항목만 적은 순서대로 넣는다. `targets`를 적지 않아도 다른 항목이 하나라도 있으면 어느 협력인지 알 수 있도록 대상·관계 줄을 협력마다 맨 앞에 붙인다. `[]`이면 Collaboration 부분을 넣지 않는다. 기본값은 `["targets", "boundary", "rationale"]`다.
- **FR-009a**: 두 목록에서 패널 안 순서는 Responsibility 부분이 항상 Collaboration 부분보다 위다. 목록이 아닌 값, 모르는 항목, 같은 항목을 두 번 적은 목록은 잘못된 값으로 보고 007 FR-005대로 그 설정만 기본값을 쓰고 안내 한 줄을 남긴다.
- **FR-010**: 섹션의 `display`가 `hidden`이면 그 섹션의 hover 목록(`hover.responsibility` 또는 `hover.collaboration`)은 값과 상관없이 빈 목록으로 동작해야 한다. 이 경우 설정 안내는 하지 않는다(정상 조합으로 본다). 두 값이 설정 파일에서 떨어져 있으므로, 설정 파일의 `hover` 그룹 주석에 이 규칙을 적는다.
- **FR-011**: Collaboration은 그 노드가 의존하는 쪽만 넣어야 한다 — 그 노드가 출발점인 협력은 `대상에 의존한다 (관계)`, 서로 의존하는 협력은 `상대와 서로 의존한다 (관계)`로 표시하고(본문 Collaboration 첫 줄에서 주어인 그 노드만 뺀 문장, 화살표 기호는 쓰지 않는다), 그 노드가 도착점인 협력(그 노드에 의존하는 쪽)은 넣지 않는다. 본문 Collaboration의 "X는 Y에 의존한다" 방향과 같다. 엣지에는 패널이 없다.
- **FR-012**: 패널 내용의 맨 윗줄은 그 노드의 이름을 굵게 표시한 줄이다(노드 표시 이름 그대로, 구조 변화 요청의 ✨/♻️/🗑️ 접두는 빼고). 그 바로 다음 줄부터 내용이 이어진다. `hover.collaboration`에 세부 분석 항목(`boundary`, `rationale`, `questions`)이 있을 때 각 세부 분석(책임의 경계, 분리 이유 & 합리성 평가, 내가 할 수 있는 질문)은 `<굵은 제목>: <문단>` 한 줄로 넣는다. 제목은 굵게 표시하고, 문단은 본문의 하위 글머리 항목들을 글머리 기호 없이 공백 하나로 이어 붙인 것이다(책임 (추상)·역할 (구체) 줄과 같은 형식). 이때 협력이 2개 이상이면 협력과 협력 사이에 빈 줄 하나를 둔다(세부 분석 항목 없이 `targets`만 있을 때는 협력마다 한 줄뿐이므로 빈 줄 없이 이어 쓴다). 패널 내용에서 책임 (추상)과 역할 (구체)은 빈 줄 없이 바로 다음 줄로 이어 붙이고, Responsibility 부분과 Collaboration 부분 사이에만 빈 줄 하나를 둔다. 패널 내용은 본문의 굵게·코드 표시를 유지하고, 본문의 Markdown 링크는 링크 없이 글자만 넣으며, 큰따옴표는 다이어그램 문법을 깨지 않는 표기로 바꿔야 한다.
- **FR-013**: 링크 대상이 없는 노드에는 링크를 만들지 않고, 클릭해도 어디로도 이동하지 않는 형태로 툴팁만 달아야 한다(003 FR-027c의 "지어내지 않기"를 그대로 따른다 — 이동 대상을 지어내지 않는다). 이 형태는 VS Code 미리보기에서 클릭 시 오류 표시나 이동을 일으켜서는 안 된다. 또 그 노드는 클릭할 수 있는 것처럼 보이면 안 되므로, 노드에 이미 있는 색상 클래스 정의에 커서를 일반 모양으로 두는 속성 하나만 덧붙인다(새 줄이나 새 클래스를 만들지 않는다). 색상 클래스는 노드마다 하나씩이므로(003 FR-008b) 이 속성은 그 노드에만 적용된다. hover 중 밑줄(FR-005)은 클릭 가능 표시가 아니라 hover 표시이므로 이 노드에도 생긴다.
- **FR-014**: 요청 문장이 hover 양이나 패널 위치를 직접 밝히면 그 요청에 한해 요청 값이 설정보다 우선한다(007 FR-006과 같은 규칙).
- **FR-015**: PNG/PDF 내보내기 결과에 FR-005 블록의 내용이 글자로 드러나서는 안 된다. GitHub 등 VS Code 미리보기가 아닌 곳에서 보이는 모양(FR-005 블록이 글자로 드러나는 것 포함)은 요구 사항에 넣지 않는다.
- **FR-016** (003 개정): 003의 "산출물에는 실제 내용만" 규칙(FR-032, SKILL.md AP-13c)의 허용 목록에 FR-005의 고정 블록을 추가한다. 이 블록은 메타 코멘트가 아니라 표시 규칙이다.
- **FR-017** (003 개정): 003의 `click` 툴팁 규칙(툴팁은 파일 이름)은 해당 노드에 패널 내용이 있을 때 그 내용으로 바뀐다. 링크 대상 자체(경로·URL)는 바뀌지 않는다. 또 003의 "링크 대상이 없으면 `click`을 두지 않는다" 규칙에, 패널 내용이 있을 때 FR-013의 이동 없는 툴팁 줄을 두는 예외를 추가한다.
- **FR-018** (007 개정): 007의 설정 옵션 목록과 옵션 정의(settings.schema.json)에 `hover.enabled`, `hover.responsibility`, `hover.collaboration`, `hover.position`을 추가하고, 사용자가 고치는 설정 파일(settings.jsonc)에 기존 형식대로 설명 주석과 함께 넣는다. 네 옵션의 모든 값의 토큰 영향 표기는 `[0]`(거의 같음)이다. 잘못된 값 처리는 007 FR-005를 따른다.
- **FR-019**: `hover.position` 값은 `bottom`(미리보기 아래쪽에 넓게 고정된 패널)과 `node`(노드 바로 아래, Mermaid 기본 위치) 중 하나이며 기본값은 `bottom`이다. 이 값은 FR-005 블록의 내용만 바꾸고, 툴팁 내용·밑줄·링크 없는 노드 처리(FR-013)에는 영향을 주지 않는다. 두 hover 목록이 모두 빈 것으로 동작하면(`hover.enabled`가 `false`인 경우 포함) 이 값은 쓰이지 않는다.
- **FR-020**: `hover.enabled` 값은 `true`와 `false` 중 하나이며 기본값은 `true`다. `false`이면 hover 기능 전체가 꺼져, `hover.responsibility`·`hover.collaboration`·`hover.position` 값과 상관없이 FR-006의 상태(이 기능 도입 전과 같은 산출물)가 된다. 이 값을 바꿔도 다른 hover 값은 그대로 남아, 다시 `true`로 바꾸면 이전 항목 설정대로 동작한다. 요청 문장에서 hover를 켜거나 끄라고 하면 그 요청에 한해 따른다(FR-014).

### Key Entities

- **노드 패널 내용**: 노드 하나에 대한 툴팁 문자열(링크 유무와 무관). Responsibility 부분(`hover.responsibility` 목록의 항목)과 Collaboration 부분(그 노드가 의존하는 협력마다 `hover.collaboration` 목록의 항목)으로 이뤄진다. 원본은 같은 파일의 본문이다.
- **패널 모양 블록**: 파일 맨 아래에 놓이는 고정 `<style>` 블록. 패널 내용이 있는 노드가 하나라도 있을 때만 존재한다.
- **hover 설정**: `hover.enabled`, `hover.responsibility`, `hover.collaboration`, `hover.position`. 설정 최상위 `hover` 그룹에 모여 있다. `hover.enabled`가 `false`이면 나머지 값과 상관없이 기능이 꺼진다. 앞의 둘은 각 섹션의 `display`와 독립적으로 정하되, `display`가 `hidden`이면 빈 목록으로 동작한다. `hover.position`은 패널 모양 블록의 내용을 정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: VS Code Markdown 미리보기에서 모든 노드(100%, 링크 유무와 무관)에 마우스를 올렸을 때, 스크롤 없이 그 노드의 Responsibility와 그 노드가 의존하는 협력 대상이 보인다.
- **SC-002**: `hover.position`이 `bottom`일 때, 패널 내용이 미리보기 화면 높이 안에 들어가는 한 어느 노드에서도 패널이 미리보기 경계에서 잘리지 않는다.
- **SC-003**: 생성 직후 모든 노드의 패널 내용이 같은 파일 본문과 100% 일치한다(설정 값에 따른 범위 안에서).

- **SC-005**: `hover.enabled`가 `false`이거나 두 hover 목록이 모두 `[]`인 설정으로 만든 산출 파일은 이 기능 도입 전 규칙으로 만든 파일과 같다.
- **SC-006**: 같은 파일을 PNG/PDF로 내보냈을 때 패널 모양 블록의 내용이 글자로 드러나는 경우가 0건이다.

## Assumptions

- 대상 미리보기는 VS Code 내장 Markdown 미리보기(Mermaid 12)다. 다른 미리보기에서의 동작은 보장하지 않는다.
- **선행 확인 결과(2026-11-14, VS Code 1.146 내장 Mermaid 미리보기)**: `docs/hover-tooltip-test/`로 다음을 확인했다 — (1) 노드 툴팁이 뜬다, (2) md 맨 아래 `<style>`이 적용된다(`bottom` 패널, `node` 툴팁 모두), (3) 링크 없는 노드의 이동 없는 `click` 줄도 툴팁이 뜨고 클릭해도 이동·오류가 없다, (4) hover 중 밑줄이 링크 유무와 상관없이 생긴다, (5) `node`에서 오른쪽 끝 노드의 툴팁이 같은 폭으로 오른쪽 끝에 붙고, 이어서 왼쪽 노드를 hover해도 제자리에 뜬다.
- **GitHub 확인 결과(2026-11-14)**: md 안 `<style>` 블록은 GitHub에서 태그째 글자로 드러난다(GFM 태그 필터). 노드 툴팁은 GitHub에서도 뜨지만, CSS가 적용되지 않아 Mermaid 기본 모양(폭 200px)으로 뜨고 다이어그램 영역 경계에서 잘린다. GitHub에서 이를 고칠 방법은 없다. 이 결과로 GitHub는 대상에서 뺐다(Clarifications 2026-11-14). 맨 끝 `<style>`과 접힌 `<details>` 안 `<style>`도 GitHub에서 확인했지만 받아들일 만하지 않았다.
- **대상 범위 밖**: GitHub를 비롯한 VS Code 미리보기 밖의 Markdown 뷰어. 이런 곳에서는 FR-005 블록이 글자로 드러날 수 있다.
- **다이어그램 안 `themeCSS`로는 툴팁 모양을 바꿀 수 없다**: Mermaid 12가 `themeCSS`의 모든 규칙을 다이어그램 범위로 묶기 때문에, 다이어그램 바깥에 그려지는 툴팁에는 적용되지 않는다(코드와 브라우저 테스트로 확인).
- `node` 모드의 최대 폭 `25em`은 한 줄 글자 수 기준으로 정했다. em은 글자 크기 기준 단위이고 한글 한 글자는 약 1em이라, 글자 크기가 바뀌어도 한 줄에 한글 약 25자가 유지된다. WCAG 2.x 1.4.8(AAA)의 한중일 문자 한 줄 40자 상한 안에 있다. em 단위로 폭을 정한 국제 규격은 없다.
- `node` 모드의 넘침 처리 근거: Mermaid(VS Code 내장 포함)는 툴팁의 왼쪽 위치를 노드 가로 중앙으로 직접 정하므로, 폭을 정하지 않으면 툴팁이 오른쪽 남은 공간만큼 좁아진다. CSS는 이 위치 값을 읽을 수 없고, SVG 안의 노드는 CSS 앵커가 될 수 없음을 확인했다. 그래서 넘칠 때 대안 위치를 시도하는 CSS 기능을 쓴다. 이 기능은 (a) 넘침 판단 기준이 첫 화면 크기라 다이어그램이 첫 화면 아래에 있으면 동작하지 않고, (b) 마지막에 쓴 대안 위치를 툴팁이 화면에서 빠질 때까지 기억한다. Mermaid는 툴팁을 투명하게만 숨기므로 (a)·(b)를 각각 기준을 문서 전체로 바꾸는 규칙과 hover 중이 아닐 때 툴팁을 화면에서 빼는 규칙으로 막는다(Chrome 157과 VS Code에서 확인).
- 패널은 스크롤할 수 없고 마우스를 노드에서 떼면 사라진다. 이는 Mermaid 툴팁의 고정 동작이며 바꾸지 않는다.
- 산출물에 더하는 표기는 Mermaid 기본 문법과 가장 짧은 표기로 한정한다(사용자 요구). 예: 링크 없는 노드의 커서는 기존 색상 클래스에 `cursor:auto`만 덧붙인다 — `cursor:default`는 `default`가 Mermaid 예약어라 다이어그램 전체가 파싱 오류로 그려지지 않으므로 쓰지 않는다.
- 툴팁을 지정하는 문법은 `click` 줄뿐이지만 링크가 필수는 아니다. 일반 브라우저(Mermaid 12.3, strict)에서 링크 대신 콜백 이름을 쓴 `click` 줄도 툴팁이 뜨고, 클릭해도 이동·오류가 없음을 확인했다. VS Code 미리보기에서도 같음을 확인했다(선행 확인 결과 (3)).
- 도구를 따로 실행할 때는 설정 파일 값만 따른다. 요청 문장으로 설정과 다른 hover 양을 썼던 파일에 도구를 다시 실행하면 설정 값으로 맞춰진다.
- 설정의 초기값(`hover.responsibility`: `["abstract", "concrete"]`, `hover.collaboration`: `["targets", "boundary", "rationale"]`)은 사용자가 정했다(007 FR-003의 "사용자가 항목별로 지정" 원칙).
- 이 기능은 `generating-architecture-views`에만 적용한다. `generating-zenuml-diagrams`의 시퀀스 다이어그램은 대상이 아니다.
- 피드백 로그 형식은 바꾸지 않는다.

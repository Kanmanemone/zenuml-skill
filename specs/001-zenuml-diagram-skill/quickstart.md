# Quickstart: `generating-zenuml-diagrams` Skill 검증

이 문서는 skill 구현 후 spec.md의 성공 기준(SC-001~SC-005)을 수동으로 검증하는 절차다. 별도의 자동화 테스트 스위트는 없다(research.md, Phase 0 — Decision: 평가 방식).

## 사전 준비

1. `.claude/skills/generating-zenuml-diagrams/SKILL.md`와 `references/syntax.md`가 존재해야 한다.
2. Claude Code에서 이 저장소를 열고, 새 대화를 시작한다(skill이 SKILL.md의 `description`을 기준으로 자동 검색되는지 확인하기 위해 명시적으로 skill 이름을 언급하지 않는다).

## 시나리오 1 — 단순하고 명확한 설명 (User Story 1 / SC-001)

**입력 예시**: "Client가 Server.getData()를 호출하는 시퀀스 다이어그램을 ZenUML로 그려줘."

**기대 결과**:
- 참가자는 `Client`, `Server` 둘만 등장한다.
- 메시지는 `getData()` 호출 하나뿐이다.
- 반환값, 예외 처리, 추가 참가자가 없다.

**검증**: 출력된 DSL을 원문 설명과 줄 단위로 대조해, 설명에 없는 요소가 하나라도 있으면 실패로 기록한다(SC-001 = 0%).

## 시나리오 2 — 조건/반복이 있는 복잡한 설명 (User Story 1, 2 / SC-001, SC-002)

**입력 예시**: "사용자가 로그인 폼을 제출하면 AuthService가 자격증명을 검증하고, 유효하면 Session을 생성해 반환하고, 유효하지 않으면 3번까지 재시도를 허용한다."

**기대 결과**:
- `if/else` 또는 이에 상응하는 조건 분기와 반복 구조가 설명된 그대로만 반영된다.
- 설명에 없는 추가 예외 처리나 로깅 참가자가 임의로 추가되지 않는다.
- 생성된 DSL이 `references/syntax.md` 문법 기준으로 유효하다(수동으로 문법 대조).

**검증**: Anti-Pattern Checklist(data-model.md AP-1~AP-5)를 결과에 대해 직접 대조한다. 전부 "예"여야 통과.

## 시나리오 3 — 모호한 설명 (User Story 3 / SC-004)

**입력 예시**: "요청이 오면 처리해서 응답한다." (주체와 대상이 불명확)

**기대 결과**:
- skill이 다이어그램을 바로 만들지 않고, "요청을 보내는 주체와 받는 주체가 누구인지" 같은 구체적 명확화 질문을 한다.
- 참가자 이름을 임의로("Client", "Server" 등) 지어내 다이어그램을 완성하지 않는다.

**검증**: 질문 없이 다이어그램이 바로 생성되면 실패로 기록한다(SC-004 = 100% 목표).

## 시나리오 4 — 범위 밖 요청 (Edge Cases)

**입력 예시 A**: "이 프로세스를 클래스 다이어그램으로 그려줘."
**기대 결과 A**: ZenUML은 시퀀스 다이어그램만 지원한다는 안내를 받는다(FR-008).

**입력 예시 B**: "이 기존 Mermaid 다이어그램을 ZenUML로 변환해줘." (Mermaid 코드 첨부)
**기대 결과 B**: 형식 변환은 현재 범위 밖이라는 안내를 받는다(Assumptions, 입력 범위).

## 시나리오 5 — `.zenuml/` 출력 파일 링크 (SC-005)

**입력 예시**: 시나리오 1과 동일 — "Client가 Server.getData()를 호출하는 시퀀스 다이어그램을 ZenUML로 그려줘."

**기대 결과**:
- 채팅 응답에는 ZenUML DSL 코드가 직접 노출되지 않고, `.zenuml/` 아래 저장된 파일을 가리키는 상대 경로 링크 한 줄만 나온다.
- 그 파일을 열면 ZenUML 원문이 Mermaid `zenuml` 코드펜스에 담겨 있다 — 번역 없이 원문 그대로가 미리보기 역할도 한다.
- VS Code(1.121+)에서 그 파일의 마크다운 프리뷰를 열면 별도 확장 없이 참가자·화살표가 그려진 도형으로 렌더링된다.
- 파일 저장이 불가능한 환경이라면, 링크 대신 ZenUML DSL 텍스트가 채팅 응답에 직접 제공된다.

**검증**: 파일 저장이 가능한 세션에서 응답에 코드 없이 링크만 붙는지, 그 파일을 열었을 때 `zenuml` 코드펜스가 실제로 도형으로 렌더링되는지 확인한다(SC-005 = 100% 목표).

## 세션 내 일관성 확인 (SC-003)

시나리오 1~3을 같은 대화 세션 안에서 연달아 요청한다. 두 번째, 세 번째 요청에서 스타일/형식 기준을 다시 설명하지 않아도 동일한 수준의 정확성과 간결함이 유지되는지 확인한다.

## 결과 기록

각 시나리오의 통과/실패와 구체적 이슈를 표로 기록해 두면, `/speckit-tasks` 이후 구현을 반복 개선할 때 회귀 확인 기준으로 재사용할 수 있다.

## Validation Results (T014, 2026-07-27)

`.claude/skills/generating-zenuml-diagrams/`가 이 세션에 실제로 인식된 직후, `Skill` 도구로 두 시나리오를 실제 호출해 검증했다(나머지는 SKILL.md 본문을 대조하는 방식으로 트레이스했다).

(3) 이 시점엔 ZenUML을 `sequenceDiagram`으로 번역해서 저장 중이었는데, "VS Code도 `zenuml`을 직접 지원하지 않을 것"이라는 가정을 실측 없이 일반화한 것이었음이 드러남 → 실제로 파일의 `zenuml` 코드펜스를 VS Code에서 열어 직접 테스트하니 정상 렌더링됨을 확인 → 번역 단계를 완전히 제거하고 `zenuml` 원문을 그대로 저장하도록 최종 수정. 같은 입력으로 다시 실행해, 응답에 코드 없이 `.zenuml/client-server-getdata.md` 링크만 나오고 파일을 열면 `zenuml` 원문이 그대로 도형으로 렌더링되는 것을 확인 |

**결론**: 실제 호출로 검증한 시나리오 중 둘(시나리오 1, 5)에서 스킬 본문 자체의 결함을 실전 검증으로 발견해 수정했다 — 특히 시나리오 5는 spec/plan/research에 문서화된 메커니즘 자체가 네 번이나 바뀐 경우로, 텍스트 로직 검토만으로는 절대 못 잡았을 결함(렌더링 지원 여부, 클라이언트 UI 동작, 그리고 "확인 안 하고 일반화한 가정")이었다. 이는 이 quickstart 문서가 존재하는 이유를 그대로 보여준다. 나머지 시나리오는 본문 대조로 충분히 확인되었으나, 새 Claude Code 세션에서 실제 자연어 요청으로 한 번 더 확인하는 것을 권장한다.

# Feature Specification: ZenUML Diagram Skill

**Feature Branch**: `001-zenuml-diagram-skill`

**Created**: 2026-07-27

**Status**: Draft

**Input**: User description: "질 좋은 Context로 깔끔한 ZenUML 다이어그램을 생성하는 Claude Skill을 만든다. 자연어로 설명한 프로세스를 입력받아, 명시되지 않은 내용을 지어내지 않고 문법적으로 정확한 ZenUML DSL을 생성한다. (`/speckit-assess-decide` go 판정, `.specify/assessments/zenuml-skill/decision.md` 인계 내용 기반)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 설명한 대로만 정확한 다이어그램 받기 (Priority: P1)

사용자가 어떤 프로세스(예: "클라이언트가 API를 호출하면 서버가 DB를 조회하고 결과를 반환한다")를 자연어로 설명하면, 그 설명에 언급된 참가자와 상호작용만 포함된 ZenUML 다이어그램 텍스트를 받는다. 설명에 없는 참가자, 메서드 호출, 예외 처리, 분기가 임의로 추가되지 않는다.

**Why this priority**: 이것이 이 기능의 존재 이유다 — 단순히 "그려주는 것"과 구별되는 핵심 가치는 "지어내지 않는다"는 정확성이며, 이게 없으면 나머지 기능은 의미가 없다.

**Independent Test**: 여러 개의 짧은 프로세스 설명을 입력하고, 생성된 다이어그램에 설명되지 않은 참가자/메시지/분기가 없는지 직접 대조해 확인할 수 있다. 이 하나만으로도 "신뢰할 수 있는 다이어그램 생성기"라는 가치를 전달한다.

**Acceptance Scenarios**:

1. **Given** "Client가 Server.getData()를 호출한다"는 한 줄짜리 설명, **When** 사용자가 다이어그램 생성을 요청하면, **Then** 결과에는 Client와 Server 두 참가자와 단일 메서드 호출만 나타나고, 반환값·예외 처리·추가 참가자는 등장하지 않는다.
2. **Given** 조건 분기와 반복이 포함된 여러 단계짜리 프로세스 설명, **When** 사용자가 다이어그램 생성을 요청하면, **Then** 설명에 언급된 조건/반복 구조만 반영되고 설명에 없는 추가 분기가 생기지 않는다.

---

### User Story 2 - 생성 전 자기검증으로 군더더기 걸러내기 (Priority: P2)

스킬이 다이어그램을 사용자에게 보여주기 전에, 흔한 안티패턴(요청되지 않은 참가자 추가, 불필요한 중첩, 근거 없는 try/catch 등)이 있는지 자체 점검하고, 문제가 있으면 수정한 뒤 결과를 내놓는다.

**Why this priority**: User Story 1이 "정확성"의 최소 기준이라면, 이 스토리는 "깔끔함"을 능동적으로 보장하는 품질 게이트다 — 리서치에서 확인된 것처럼 프롬프트 지시만으로는 장황함이 완전히 사라지지 않으므로, 명시적 자기검증 단계가 필요하다.

**Independent Test**: 의도적으로 장황해지기 쉬운 설명(예: 여러 참가자가 얽힌 복잡한 플로우)을 입력해, 결과물에 안티패턴 체크리스트 위반이 없는지 확인하는 것만으로 이 스토리의 가치를 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 복잡한 다단계 프로세스 설명, **When** 스킬이 초안을 생성하면, **Then** 사용자에게 보여주기 전에 안티패턴 체크리스트와 대조하고, 위반 사항이 있으면 수정한 결과를 제시한다.
2. **Given** 자기검증 결과 문제가 발견되지 않는 간단한 설명, **When** 스킬이 다이어그램을 생성하면, **Then** 불필요한 지연 없이 바로 결과를 제시한다.

---

### User Story 3 - 설명이 불충분할 때 지어내지 않고 되묻기 (Priority: P3)

사용자의 설명이 다이어그램을 정확히 그리기에 정보가 부족할 때(예: 누가 누구를 호출하는지 불명확), 스킬은 임의로 내용을 채워 넣지 않고 사용자에게 명확화를 요청한다.

**Why this priority**: User Story 1·2보다 발생 빈도는 낮지만, "지어내지 않는다"는 핵심 원칙이 애매한 입력 상황에서도 지켜지도록 보장하는 안전장치다.

**Independent Test**: 의도적으로 모호한 설명(예: 주체가 불명확한 문장)을 입력해, 스킬이 다이어그램을 즉시 만들어내는 대신 명확화 질문을 하는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 호출 주체나 순서가 불명확한 설명, **When** 사용자가 다이어그램 생성을 요청하면, **Then** 스킬은 빠진 정보를 지어내는 대신 구체적인 명확화 질문을 한다.

---

### Edge Cases

- 사용자가 ZenUML이 지원하지 않는 다이어그램 유형(클래스 다이어그램, 배포 다이어그램 등)을 요청하면, 스킬은 ZenUML이 시퀀스 다이어그램만 지원한다는 점을 명확히 안내한다.
- 사용자가 기존 Mermaid/PlantUML 다이어그램이나 코드베이스를 ZenUML로 변환해달라고 요청하면, 스킬은 이것이 현재 범위 밖임을 안내한다(자연어 설명 입력만 지원).
- 참가자 수가 매우 많거나 프로세스가 지나치게 복잡한 설명이 주어지면, 스킬은 그대로 반영하되 결과가 읽기 어려워질 수 있음을 사용자에게 알린다.
- 사용자가 완성된 다이어그램을 실제로 렌더링해서 보고 싶어 하면, FR-011에 따라 저장되는 파일이 이미 Mermaid `zenuml` 코드펜스로 렌더링 가능하므로 별도 렌더링 도구 없이 그 파일을 열어 확인할 수 있음을 안내한다.
- 파일 저장이 불가능한 환경(예: 파일시스템 접근이 없는 실행 환경)에서는, `.zenuml/` 파일 링크 대신 채팅 응답에 ZenUML DSL 텍스트를 코드 블록으로 직접 제공하고 그 사실을 짧게 안내한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 스킬은 사용자의 자연어 설명에 명시적으로 언급되었거나 명확히 함의된 참가자·메시지·제어 흐름만 사용해 ZenUML DSL을 생성해야 한다.
- **FR-002**: 스킬은 사용자 입력에 없는 참가자, 메서드 호출, 분기, 예외 처리 블록을 임의로 추가해서는 안 된다.
- **FR-003**: 스킬은 문법적으로 유효한 ZenUML DSL(참가자 선언, 동기/비동기 메시지, 조건문, 반복문, 반환값 등)을 생성해야 하며, 이는 스킬에 번들링된 ZenUML DSL 문법 레퍼런스를 기준으로 한다.
- **FR-004**: 스킬은 ZenUML DSL 문법 레퍼런스를 스킬 디렉터리 내부에 번들링하여, 별도의 네트워크 접근 없이도 정확한 문법으로 다이어그램을 생성할 수 있어야 한다.
- **FR-005**: 스킬은 흔한 안티패턴(요청되지 않은 참가자/메시지 추가, 불필요한 중첩, 근거 없는 예외 처리 등) 목록을 유지하고, 다이어그램 초안을 사용자에게 제시하기 전에 이 목록과 대조해 자체 점검해야 한다.
- **FR-006**: 자체 점검에서 안티패턴 위반이 발견되면, 스킬은 결과를 사용자에게 보여주기 전에 수정해야 한다.
- **FR-007**: 사용자의 설명이 다이어그램을 정확히 구성하기에 불충분하거나 모호할 때, 스킬은 내용을 지어내는 대신 사용자에게 구체적인 명확화 질문을 해야 한다.
- **FR-008**: 사용자가 ZenUML이 지원하지 않는 다이어그램 유형을 요청하면, 스킬은 이를 명확히 안내해야 한다(ZenUML은 시퀀스 다이어그램만 지원).
- **FR-009**: 스킬에 번들링된 문법 레퍼런스는 원출처(mermaid-js/zenuml-core의 DSL_SYNTAX.md, MIT 라이선스)에 대한 출처 표기를 유지해야 한다.
- **FR-010**: 스킬의 주 출력물은 렌더링된 이미지가 아닌 ZenUML DSL 텍스트여야 한다.
- **FR-011**: 자기검증(FR-005~FR-006)을 통과한 다이어그램은 채팅 응답에 코드로 직접 노출하지 않고, 프로젝트 저장소의 `.zenuml/` 디렉터리 아래에 파일로 저장한 뒤 그 파일을 가리키는 상대 경로 링크만 응답에 남겨야 한다. 저장되는 파일은 ZenUML DSL을 Mermaid `zenuml` 코드펜스에 담아야 한다 — 이는 원문 그 자체이면서 동시에 시각적 미리보기 역할을 한다(VS Code 마크다운 프리뷰가 `zenuml` 타입을 네이티브로 렌더링함이 실측으로 확인됨 — research.md 참조). `.zenuml/`은 저장소의 `.gitignore`에 포함되어야 한다. 파일 저장이 불가능한 환경에서는 채팅 응답에 ZenUML DSL 텍스트를 직접 제공해야 한다.

### Key Entities *(include if feature involves data)*

- **ZenUML 다이어그램(출력물)**: 사용자가 설명한 프로세스를 나타내는 참가자와 메시지들의 순서로 구성된 ZenUML DSL 텍스트.
- **문법 레퍼런스**: 스킬에 번들링된, ZenUML DSL 문법 규칙 문서.
- **안티패턴 체크리스트**: 생성된 다이어그램을 사용자에게 보여주기 전에 대조하는, "군더더기 없음"을 판단하는 기준 목록.
- **출력 파일**: `.zenuml/` 아래 저장되는 파일. ZenUML DSL을 Mermaid `zenuml` 코드펜스에 담아, 원문과 렌더링 가능한 미리보기를 동시에 제공한다. 채팅 응답에는 이 파일을 가리키는 상대 경로 링크만 노출된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 프로세스 설명을 입력했을 때, 생성된 다이어그램에 설명되지 않은 참가자·메시지·분기가 포함되는 비율이 0%다(대표 테스트 시나리오 기준).
- **SC-002**: 조건 분기, 반복, 중첩 호출을 포함한 다양한 테스트 시나리오에서, 생성된 다이어그램 텍스트가 문법 오류 없이 유효한 ZenUML DSL로 판정된다.
- **SC-003**: 같은 세션 내에서 여러 번 다이어그램을 요청해도, 사용자가 스타일/형식 기준을 다시 설명할 필요 없이 일관된 결과를 받는다.
- **SC-004**: 설명이 불충분해 다이어그램을 정확히 그릴 수 없는 경우, 스킬이 내용을 지어내지 않고 명확화 질문을 하는 비율이 100%다(대표 테스트 시나리오 기준).
- **SC-005**: 파일 저장이 가능한 환경에서, 자기검증을 통과한 모든 다이어그램에 대해 채팅 응답에 코드가 노출되지 않고 `.zenuml/` 파일 링크만 제공되는 비율이 100%이며, 그 파일을 열었을 때 Mermaid 미리보기가 실제로 렌더링되는 비율이 100%다(대표 테스트 시나리오 기준).

## Assumptions

- **대상 렌더러/문법 기준**: `mermaid-js/zenuml-core`의 DSL 문법을 1차 기준으로 삼는다 (`.specify/assessments/zenuml-skill/concept.md` Option B에서 이미 확정됨). `zenuml.com` 상업 제품이나 VS Code 확장과의 100% 호환은 보장하지 않는다.
- **사용자 범위**: 현재는 저장소 소유자 1인의 개인 사용을 전제로 한다. 팀/조직 단위 배포나 거버넌스는 범위 밖이다(`.specify/assessments/zenuml-skill/problem.md` Non-Goals에서 이미 확정됨).
- **입력 범위**: 자연어 프로세스 설명만 입력으로 지원한다. 기존 코드베이스 분석이나 Mermaid/PlantUML 등 다른 형식으로부터의 변환은 이번 범위에 포함하지 않는다.
- **출력 형태**: 주 출력물은 렌더링된 이미지가 아닌 ZenUML DSL 텍스트다. FR-011에 따라, 이 텍스트는 채팅 응답이 아니라 `.zenuml/` 아래 파일에 Mermaid `zenuml` 코드펜스 형태로 저장되고, 응답에는 그 파일 링크만 노출된다 — Claude Artifact 방식은 발행 즉시 클라이언트가 미리보기를 자동으로 띄우는 동작을 억제할 방법이 없어 폐기했고(research.md 참조), 파일 링크는 사용자가 직접 클릭해야만 열리므로 이 문제를 근본적으로 피한다. VS Code 1.121+는 마크다운 프리뷰에서 Mermaid `zenuml` 타입까지 네이티브로 렌더링하므로(실측 확인), 원문을 다른 문법으로 번역할 필요 없이 그대로 저장하면 되고 별도 확장이나 렌더러 구축도 필요 없다 — 이는 새 렌더러를 만드는 것이 아니라 에디터가 이미 갖춘 기능을 활용하는 것이며, `.specify/assessments/zenuml-skill/problem.md` Non-Goals의 "렌더링 미리보기 환경 자체 구축"과는 구분된다.
- **모호한 입력 처리 방식**: 이 스킬은 대화형 Claude Code 세션에서 사용되므로, 정보가 부족할 때는 조용히 가정하기보다 사용자에게 직접 되묻는 것을 기본 동작으로 한다.
- **라이선스 고지 형식**: 번들링된 문법 레퍼런스 파일 상단에 원출처(mermaid-js/zenuml-core, MIT 라이선스)를 명시하는 주석/헤더를 표준 형식으로 유지한다.

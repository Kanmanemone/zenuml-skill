## User Scenarios & Testing *(mandatory)*

### User Story 1 - 다이어그램을 처음 생성하면 산출물과 이력이 함께 남는다 (Priority: P1) 🎯 MVP

사용자가 `generating-zenuml-diagrams`로 다이어그램을 처음 요청한다. 시스템은 다이어그램 산출물 파일과, 이번 요청·응답을 담은 로그 파일을 각각 하나씩 만든다.

**Why this priority**: 이후 모든 재생성·이력 누적의 전제조건이다. 이 단계만으로도 "요청과 결과가 어딘가에 남는다"는 최소 가치가 성립한다.

**Independent Test**: 다이어그램 하나를 새로 요청한다. `.zenuml/<slug>.md`(다이어그램만)와 로그 파일(요청 원문 + 응답)이 둘 다 만들어졌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 처음으로 다이어그램을 요청한 상태, **When** 시스템이 다이어그램을 성공적으로 생성하면, **Then** `.zenuml/<slug>.md`(다이어그램 산출물)와 그 다이어그램 전용 로그 파일이 함께 만들어지고, 로그 파일에는 최초 요청 원문과 그에 대한 응답이 담긴다.

---

### User Story 2 - 재생성을 요청하면 산출물은 교체되고 이력은 누적된다 (Priority: P1)

사용자가 이미 생성된 다이어그램에 대해 자연스럽게 변경을 요청한다("~로 고쳐줘" 등 — 정해진 문구나 확인 질문 없이). 시스템은 그 요청을 반영해 다이어그램을 다시 생성하고, 산출물 파일은 새 내용으로 완전히 교체하며, 로그 파일에는 기존 내용을 지우지 않고 이번 요청·응답을 새 라운드로 이어붙인다.

**Why this priority**: 이 기능의 핵심 가치 — "무엇을 왜 고쳤는지"가 산출물이 아니라 로그에만 쌓이도록 분리하는 것 — 가 여기서 성립한다.

**Independent Test**: User Story 1로 만들어진 다이어그램에 대해 변경을 요청한다. `.zenuml/<slug>.md`가 새 다이어그램 하나만 담고 있고(이전 내용은 사라짐), 로그 파일에는 최초 라운드와 이번 라운드가 모두 남아 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이미 다이어그램 산출물과 로그 파일이 존재하는 상태, **When** 사용자가 그 다이어그램에 대한 변경을 요청하면, **Then** 시스템은 다이어그램을 재생성하고, `.zenuml/<slug>.md`를 새 내용으로 완전히 교체하며, 로그 파일에는 기존 라운드를 그대로 둔 채 이번 요청·응답을 새 라운드로 추가한다.

---

### User Story 3 - 여러 번 재생성해도 이력이 하나도 유실되지 않는다 (Priority: P2)

같은 다이어그램에 대해 재생성 요청이 여러 차례 이어진다. 매번 산출물은 최신 상태로 교체되지만, 로그 파일에는 모든 라운드가 순서대로 보존된다.

**Why this priority**: 여러 차례 다듬어지는 경우가 흔하며, 중간 라운드가 유실되면 "무엇을 몇 번, 어떤 순서로 고쳤는지"라는 이력의 핵심 가치가 사라진다. User Story 2가 성립해야 검증 가능하므로 P2.

**Independent Test**: 같은 다이어그램에 재생성 요청을 연속 두 번 보낸다. `.zenuml/<slug>.md`는 세 번째(최신) 버전만 담고, 로그 파일에는 최초·1차 재생성·2차 재생성 라운드가 모두 순서대로 남아 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이미 한 차례 재생성되어 로그에 라운드가 하나 쌓인 상태, **When** 또 다른 변경을 요청하면, **Then** 산출물은 다시 교체되고 로그에는 새 라운드가 이전 라운드를 지우지 않고 추가된다.

---

### User Story 4 - 실제로 인용된 로그만 선별적으로 버전관리에 편입한다 (Priority: P3)

로그 디렉토리에 여러 다이어그램의 이력이 쌓여 있다. 어떤 작업이 특정 로그 파일을 실제로 인용하면, 그 파일 하나만 버전관리에 편입되고 나머지는 그대로 남는다.

**Why this priority**: 이 기능의 장기 목표(이력을 미래 개선의 재료로 쓰기)를 완성하는 마지막 조각이지만, User Story 1~3이 만드는 로그 자체가 먼저 존재해야 성립하므로 가장 낮은 우선순위다.

**Independent Test**: 쌓인 로그 파일 중 하나를 실제로 인용한 뒤 그 파일만 버전관리 대상으로 바뀌고 나머지는 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 아직 버전관리 대상이 아닌 로그 파일이 여러 개 쌓여 있는 상태, **When** 그중 하나가 실제로 인용되면, **Then** 그 로그 파일 하나만 버전관리에 편입되고 나머지는 그대로 미편입 상태로 남는다.

---

### Edge Cases

- 사용자의 요청이 모호해 다이어그램 자체가 생성되지 못하고 질문으로 끝난 경우, 산출물 파일도 로그 파일도 만들어지지 않는다.
- 현재 환경이 파일을 저장할 수 없어 다이어그램이 채팅 코드블록으로만 제공된 경우, 애초에 파일이 없으므로 이력도 남지 않는다.
- 사용자가 다이어그램과 무관한 대화를 이어가거나 별다른 변경 요청을 하지 않으면, 그것이 곧 "만족"이며 어떤 파일도 추가로 바뀌지 않는다 — 별도의 확인 질문이나 선택지는 없다.
- 하나의 다이어그램에 대해 매우 많은 라운드(예: 10회 이상)가 누적되어 로그 파일이 길어지는 경우에도, 시스템은 기존 라운드를 요약하거나 잘라내지 않고 전부 보존한다.
- 사용자의 후속 메시지가 "이 다이어그램을 고쳐달라"는 요청인지 아니면 완전히 새로운 무관한 요청인지 애매한 경우, 시스템은 대화 맥락(직전에 생성한 다이어그램을 두고 하는 말인지)으로 판단한다 — 정해진 트리거 문구는 없다.
- 그렇게 대화 맥락으로 살펴봐도 재생성인지 완전히 새로운 요청인지 끝내 판단하기 어려운 경우, 시스템은 다이어그램을 만들거나 어떤 파일도 건드리지 않고 어느 쪽인지 구체적으로 되묻는다.
- 완전히 새로운(무관한) 다이어그램 요청인데, 그 설명에서 도출한 이름이 이미 존재하는 다른 다이어그램 파일과 우연히 겹치는 경우, 시스템은 기존 이름 충돌 규칙(다른 이름으로 구분해 저장)을 적용해 별개의 다이어그램으로 취급한다 — 기존 파일을 덮어쓰지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 다이어그램이 처음 성공적으로 생성될 때, 시스템은 다이어그램 산출물 파일(`.zenuml/<slug>.md`)과 그 다이어그램 전용 로그 파일(`.zenuml/log/<slug>.md`)을 각각 하나씩 만들어야 하며, 로그 파일에는 최초 요청 내용(그 요청을 확정 짓기까지 오간, 명확화 질문·답변 등 관련된 여러 턴이 있었다면 그것들을 정리한 것 포함)과 그에 대한 응답을 기록해야 한다.
- **FR-002**: 사용자가 이미 생성된 다이어그램에 대해 변경을 요청하면, 시스템은 별도의 확인 질문이나 선택지 없이 그 요청을 반영해 다이어그램을 재생성해야 한다.
- **FR-003**: 재생성이 발생하면, 시스템은 다이어그램 산출물 파일을 새로 생성된 내용으로 완전히 교체해야 한다 — 이전 내용은 그 파일에 남지 않는다.
- **FR-004**: 재생성이 발생하면, 시스템은 로그 파일의 기존 내용을 지우지 않고 이번 라운드의 요청 내용(직전 라운드 이후 이 재생성에 실제로 기여한 관련 턴들을 정리한 것)과 응답을 새 라운드로 이어붙여야 한다.
- **FR-005**: 사용자가 추가 변경을 요청하지 않는 한, 시스템은 어떤 파일도 추가로 생성하거나 수정해서는 안 된다.
- **FR-006**: 로그 파일이 위치하는 디렉토리는 기본적으로 버전관리 대상에서 제외되어야 한다.
- **FR-007**: 이후 어떤 Spec Kit 관련 작업이 특정 로그 파일을 실제 근거 자료로 인용하는 시점에, 그 로그 파일 하나만 선별적으로 버전관리에 편입되어야 하며, 인용되지 않은 다른 로그 파일은 계속 미편입 상태로 남아야 한다.
- **FR-008**: 시스템은 로그 파일의 내용을 자동으로 요약하거나 로그 전반에서 패턴을 자동으로 탐지해서는 안 된다 — 어떤 로그를 재료로 쓸지는 항상 사람이 직접 판단한다.
- **FR-009**: 다이어그램이 생성되지 못하고 대화가 끝난 경우(예: 요청이 모호해 질문으로 종료), 시스템은 산출물 파일과 로그 파일 어느 쪽도 만들어서는 안 된다.

### Key Entities

- **다이어그램 산출물**: `.zenuml/<slug>.md`. 항상 "현재" 다이어그램 하나만 담는다 — 재생성될 때마다 전체가 교체된다. 과거 버전은 여기 남지 않는다.
- **다이어그램 피드백 로그**: 다이어그램 산출물과는 별개의 파일 — `.zenuml/log/<slug>.md`(계획 단계에서 확정, `/speckit-plan` 참고). 최초 요청·응답부터 시작해 재생성 라운드가 순서대로 계속 이어붙는 append-only 이력 문서. 개선 요청이 한 번도 없었던 다이어그램도 최초 라운드는 이미 담고 있다(User Story 1).
- **교정 라운드**: 로그 파일 안의 한 단위. 그 시점의 요청 내용(단일 메시지 하나가 아니라, 직전 라운드 이후 이 라운드를 확정 짓는 데 실제로 기여한 관련 턴들 — 명확화 질문과 그 답변 등 — 을 모아 무관한 내용은 제외하고 정리한 것)과, 그에 대한 응답(생성/재생성된 다이어그램 포함)으로 구성된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 다이어그램이 처음 생성될 때마다 예외 없이 산출물 파일과 로그 파일이 함께 만들어진다. (baseline: 0 — 현재 로그 파일이라는 개념 자체가 없다)
- **SC-002**: 재생성이 몇 차례 이어지더라도, 다이어그램 산출물 파일은 항상 가장 최근 버전 하나만 담고 있다.
- **SC-003**: 재생성이 몇 차례 이어지더라도, 로그 파일에는 이전 라운드가 하나도 유실되지 않고 순서대로 남아 있다.
- **SC-004**: 별도의 확인 질문 없이도, 사용자가 후속 변경을 요청하지 않으면 어떤 파일도 추가로 바뀌지 않는다.
- **SC-005** *(장기·정성적 지표)*: 최소 1건 이상의 향후 Spec Kit 실행이 다이어그램 피드백 로그의 특정 항목을 실제 근거 자료로 인용한다. (baseline: 0 — 메커니즘 자체가 아직 없다)

## Assumptions

- 사용자의 후속 메시지가 "재생성 요청"인지는 정해진 트리거 문구나 확인 질문 UI가 아니라, 에이전트가 대화 맥락(직전에 생성한 다이어그램을 두고 변경을 요구하는지)으로 판단한다.
- 로그 파일은 `.zenuml/log/<slug>.md`에 위치한다(`/speckit-plan` 단계에서 확정, research.md Decision: 로그 파일 위치 참고). "응답" 필드에는 생성/재생성된 ZenUML 코드가 포함된다.
- 로그 파일이 어떤 Spec Kit 실행의 재료로 인용된 뒤에도 그 파일은 삭제되거나 "소비됨"으로 표시되지 않고 그대로 남는다 — 소비 상태를 자동으로 추적하는 기능은 범위 밖이다.
- "실제로 인용하는 시점"을 감지해 버전관리 편입을 트리거하는 정확한 메커니즘은 계획 단계에서 확정하되, 다른 Spec Kit 스킬 파일을 수정해 자동화하지 않는다(이 메커니즘은 `generating-zenuml-diagrams` 스킬 하나에만 적용된다).
- 인용되지 않은 채 로컬에만 남아 있는 로그 파일이 기기 교체나 실수로 유실될 수 있다는 점은 감내 가능한 트레이드오프로 받아들여졌다.

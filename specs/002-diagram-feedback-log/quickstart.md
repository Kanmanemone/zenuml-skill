# Quickstart: 다이어그램별 개선 이력 로깅 검증

이 문서는 구현 후 spec.md의 성공 기준(SC-001~SC-005)을 수동으로 검증하는 절차다. feature 001과 동일하게 별도의 자동화 테스트 스위트는 없다(research.md 계승 — evaluation-driven 접근).

## 사전 준비

1. `.claude/skills/generating-zenuml-diagrams/SKILL.md`에 "요청 종류 판단"(0단계) 절이 워크플로 맨 앞에 있고, 그 아래로 최초 생성/재생성/인용 스테이징 절이 추가되어 있어야 한다.
2. Claude Code에서 이 저장소를 열고 새 대화를 시작한다.
3. `git status`로 시작 시점에 `.zenuml/` 아래 추적되지 않은 파일이 없는지 확인해 둔다(검증 후 비교 기준).

## 시나리오 0 — 요청 종류 판단이 정확한가 (가장 중요, 최우선 검증)

이 판단이 틀리면 이후 모든 시나리오가 무의미해지므로 가장 먼저, 가장 꼼꼼히 확인한다.

**0-A. 재생성을 재생성으로 정확히 인식하는가**
입력: "Client가 Server.getData()를 호출하는 시퀀스 다이어그램을 ZenUML로 그려줘." → 이어서 "Server 대신 Gateway를 거치는 걸로 고쳐줘."
기대 결과: 두 번째 요청이 **재생성**으로 판단되어 `.zenuml/<slug>.md`가 교체되고 `.zenuml/log/<slug>.md`에 Round 2가 추가된다 — 새로운 별개의 다이어그램(새 slug)으로 오인해 별도 파일 쌍을 만들지 않는다.

**0-B. 무관한 새 요청을 재생성으로 오인하지 않는가**
입력: 0-A 이후, 전혀 다른 프로세스("결제 승인 시퀀스를 그려줘")를 요청.
기대 결과: **최초 생성**으로 판단되어 다른 slug의 새 파일 쌍(`.zenuml/<slug2>.md`, `.zenuml/log/<slug2>.md`)이 만들어진다 — 직전 다이어그램(Client/Server/Gateway)을 실수로 교체하지 않는다.

**0-C. slug 충돌로 인한 새 요청을 재생성으로 오인하지 않는가**
입력: 0-A와 완전히 무관한 새 프로세스인데 우연히 같은 slug가 도출되는 요청(예: 참가자 이름이 비슷해 동일한 kebab-case 이름이 나오는 경우).
기대 결과: **slug 충돌로 인한 새 요청**으로 판단되어 기존 `-2`/`-3` 규칙으로 새 변형 slug의 파일 쌍이 만들어진다 — 기존 `.zenuml/<slug>.md`(0-A의 결과)를 덮어쓰지 않는다.

**0-D. 판단이 애매하면 추측하지 않고 되묻는가**
입력: 맥락상 재생성인지 새 요청인지 모호하게 해석될 수 있는 짧은 후속 메시지.
기대 결과: 다이어그램을 만들거나 파일을 건드리지 않고, "지금 만든 다이어그램을 고치는 건가요, 아니면 새로 만드는 건가요?"류의 구체적 질문으로 되묻는다.

## 시나리오 1 — 최초 생성 시 두 파일이 함께 만들어진다 (User Story 1 / SC-001)

**입력 예시**: "Client가 Server.getData()를 호출하는 시퀀스 다이어그램을 ZenUML로 그려줘."

**기대 결과**: `.zenuml/<slug>.md`(다이어그램만)와 `.zenuml/log/<slug>.md`(최초 요청 원문 + 응답, `## Round 1`)가 함께 만들어진다.

**검증**: 두 파일이 모두 존재하는지, 로그 파일의 Round 1 요청 원문이 실제 입력과 일치하는지 확인한다.

## 시나리오 2 — 재생성 시 산출물은 교체, 로그는 누적 (User Story 2 / SC-002, SC-003)

**입력 예시**: 시나리오 1에 이어 "Server 대신 Gateway를 거치는 걸로 고쳐줘."

**기대 결과**: `.zenuml/<slug>.md`는 새 다이어그램(Gateway 경유) 하나만 담고 있고, 이전(Server 직접 호출) 내용은 그 파일에서 사라졌다. `.zenuml/log/<slug>.md`에는 Round 1(원본)과 Round 2(Gateway로 변경)가 모두 순서대로 남아 있다.

**검증**: 산출물 파일에 Gateway 관련 내용만 있는지(Server 직접 호출 내용이 없는지), 로그 파일에는 두 라운드가 모두 남아 있는지 확인한다(SC-002, SC-003).

## 시나리오 3 — 별다른 요청이 없으면 아무 것도 바뀌지 않는다 (Edge Case / SC-004)

**입력 예시**: 시나리오 2 이후, 다이어그램과 무관한 다른 대화를 이어간다(추가 변경 요청 없음).

**기대 결과**: `.zenuml/<slug>.md`, `.zenuml/log/<slug>.md` 둘 다 시나리오 2 이후로 전혀 바뀌지 않는다 — 별도의 확인 질문이나 선택지 없이도 "만족"이 자연스럽게 성립한다.

**검증**: 두 파일의 mtime과 내용이 이후 대화 동안 바뀌지 않았는지 확인한다.

## 시나리오 4 — 인용 시 로그 파일만 선별적으로 스테이징 (User Story 4 / SC-005)

**입력 예시**: 누적된 `.zenuml/log/<slug>.md`를, 별도 작업(예: `/speckit-assess-research`를 사용한 가상의 후속 조사)에서 실제로 읽고 근거 자료로 인용한다고 가정하고, SKILL.md의 안내에 따라 `git add -f .zenuml/log/<slug>.md`를 실행한다.

**기대 결과**: `git status`에서 그 로그 파일 하나만 "staged"로 표시된다. `.zenuml/<slug>.md`(산출물)나 다른 다이어그램의 로그 파일은 여전히 미스테이징 상태다.

**검증**: `git status`와 `git status --ignored` 출력을 비교해 인용된 로그 파일 하나만 스테이징 상태로 전환됐는지 확인한다.

## 시나리오 5 — 다이어그램이 생성되지 못한 경우 아무 파일도 생기지 않는다 (Edge Case / FR-009)

**입력 예시 A**: "요청이 오면 처리해서 응답한다." (모호한 설명 — 명확화 질문으로 끝남)
**입력 예시 B**: "이 프로세스를 클래스 다이어그램으로 그려줘." (범위 밖 요청)

**기대 결과**: 두 경우 모두 다이어그램이 생성되지 않으므로 산출물 파일도 로그 파일도 생기지 않는다.

**검증**: `git status --ignored`에 새 파일이 없는지 확인한다.

## 결과 기록

각 시나리오의 통과/실패와 구체적 이슈를 표로 기록해 두면, `/speckit-tasks` 이후 구현을 반복 개선할 때 회귀 확인 기준으로 재사용할 수 있다. 특히 시나리오 0(요청 종류 판단)은 실제 대화로 여러 차례 반복 검증하는 것을 권장한다 — feature 001의 quickstart.md도 비슷한 판단 로직(명확화 필요 여부)에서 실제 호출로만 발견되는 결함이 있었다.

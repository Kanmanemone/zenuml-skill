# Phase 0 Research: 다이어그램별 개선 이력 로깅

이 문서는 `plan.md`의 Technical Context와 spec.md의 Assumptions에 남아 있던 구현 수준 결정 사항을 정리한다. 문제/증거/컨셉 수준 조사는 이미 `.specify/assessments/diagram-feedback-log/`에서 여러 차례 반복 검증을 거쳐 완료되었으므로, 여기서는 그 결론을 계승해 **skill을 실제로 어떻게 확장할지**에 대한 남은 결정만 다룬다.

> **개정 이력**: 이 기능은 계획 단계에서만 세 차례 아키텍처가 바뀌었다 — (1) 별도 로그 디렉토리 + 재생성마다 새 스냅샷 파일, (2) 별도 파일 없이 다이어그램 파일 하나에 전부 누적, (3, 최종) 확인 질문 UI를 완전히 없애고 다이어그램 산출물(교체됨)과 별도 로그 파일(누적됨)로 다시 분리. 이 문서는 (3)을 반영한 최종본이다.

## Decision: 요청 종류 판단 절차 — 워크플로의 첫 단계

- **Decision**: 다이어그램을 만들기 전에, 이 요청이 다음 셋 중 무엇인지부터 판정한다.
  1. **재생성**: 이번 대화(세션) 안에서 방금 제시한 다이어그램에 대한 변경·수정 요청("Server 대신 Gateway로", "반환값도 추가해줘" 등, 직전 결과물을 두고 하는 말).
  2. **최초 생성**: 완전히 새로운 프로세스 설명이며, 도출된 slug와 같은 이름의 파일이 아직 없음.
  3. **slug 충돌로 인한 새 요청**: 완전히 새로운 프로세스 설명인데, 도출된 slug가 이미 존재하는(그러나 지금 요청과는 무관한) 다른 다이어그램 파일과 우연히 겹침 — feature 001의 기존 "이름 충돌 시 `-2`, `-3`" 규칙을 그대로 적용해 새 slug 변형으로 최초 생성 취급한다.
  판정이 애매하면 추측하지 않고, feature 001이 이미 갖고 있는 "명확화 질문" 패턴을 재사용해 사용자에게 되묻는다(예: "지금 만든 다이어그램을 고치는 건가요, 아니면 새로 만드는 건가요?").
- **Rationale**: 사용자가 이번 계획에서 가장 강하게 요구한 지점이다 — "agent 입장에서 이게 '최초 생성'인지 '재생성'인지의 선택을 잘해야 한다. 그 절차를 가장 먼저." 이 판단이 틀리면 (a) 재생성인데 최초 생성으로 오판 → 기존 산출물을 안 건드리고 엉뚱한 `-2` 파일을 만들어 원래 로그와 연결이 끊기거나, (b) 최초 생성인데 재생성으로 오판 → 무관한 기존 파일을 실수로 덮어써 그 이력을 통째로 잃는(FR-003의 "교체"가 되돌릴 수 없는 동작이라는 점에서 특히 위험) 되돌리기 어려운 실수로 이어진다. 그래서 이 판단을 그 무엇보다 먼저, 명시적인 별도 단계로 두어야 한다.
- **Alternatives considered**: 판단 절차 없이 "재생성 같아 보이면 재생성으로 처리"하는 암묵적 추론만 SKILL.md 곳곳에 흩어 두기 — 사용자가 명시적으로 "그 절차를 가장 먼저 하도록 파이프라인을 짜라"고 요구했으므로, 명시적이고 순서가 고정된 별도 절차로 만드는 쪽을 채택.

## Decision: 확인 질문/선택 UI를 전혀 쓰지 않는다

- **Decision**: AskUserQuestion이든 하드코딩된 텍스트 메뉴든, 어떤 형태의 확인 질문도 두지 않는다. 사용자가 후속 변경을 요청하면 그 자체가 재생성 트리거이고, 요청이 없으면 그 자체가 만족이다.
- **Rationale**: `/speckit-clarify` 세션에서 사용자가 명시적으로 확인 — "그럼 애초에 물어볼 필요가 없어지잖아." 이전에 검토했던 AskUserQuestion(라벨 제약), 하드코딩 텍스트 메뉴(문자열 매칭 방식) 관련 논의는 전부 이 결정으로 대체되어 폐기됐다.
- **Alternatives considered**: AskUserQuestion 재활용, 하드코딩 텍스트 메뉴 — 둘 다 이전 세션들에서 검토했으나 최종적으로 "질문 자체가 불필요하다"는 결정으로 대체됨(spec.md Clarifications 참고).

## Decision: 로그 파일 위치

- **Decision**: `.zenuml/log/<slug>.md` — 다이어그램 산출물(`.zenuml/<slug>.md`)과 같은 slug, 같은 상위 디렉토리(`.zenuml/`)의 `log/` 하위 디렉토리.
- **Rationale**: `.zenuml/` 하위에 두면 기존 gitignore 규칙(`.gitignore:10`)이 하위 디렉토리까지 그대로 커버해 새 gitignore 항목이 필요 없다. slug를 그대로 재사용하면 어떤 로그가 어떤 산출물과 대응하는지 파일 시스템만 보고도 알 수 있다. 산출물과 로그를 같은 파일로 합치지 않고 분리한 이유는 spec.md의 최종 결정 그대로다 — 산출물은 "지금 상태"만 필요하고(재생성마다 교체), 로그는 "지금까지의 전체 이력"이 필요하므로(재생성마다 append) 두 파일의 갱신 방식 자체가 근본적으로 다르다.
- **Alternatives considered**: 산출물과 로그를 한 파일에 누적(계획 2단계에서 시도했으나 spec.md 최종 결정에서 다시 분리됨 — "요청·응답이 계속 쌓이는 파일"과 "항상 최신 상태만 보여주는 파일"은 목적이 달라 하나로 합치면 두 목적 모두 어중간해짐); 로그를 `.zenuml/` 밖 별도 최상위 디렉토리에 두기(새 gitignore 항목이 필요해지고 산출물과의 연관성이 경로만으로 드러나지 않아 기각).

## Decision: 다이어그램 산출물은 전체 교체, 로그는 append

- **Decision**: `.zenuml/<slug>.md`는 재생성마다 파일 내용을 완전히 새로 씀(교체) — 과거 버전은 남지 않는다. `.zenuml/log/<slug>.md`는 최초 요청+응답으로 시작해, 재생성마다 `## Round N — <날짜>` 절(요청 텍스트 + 응답)을 파일 끝에 이어붙인다. 기존 라운드는 절대 수정·삭제하지 않는다.
- **Rationale**: spec.md FR-003·FR-004가 이미 이렇게 확정했다. 산출물은 "지금 보여줄 다이어그램 하나"만 있으면 충분하고(VS Code 프리뷰로 바로 확인하는 용도), 이력은 로그 파일이 전담하므로 산출물에 여러 버전을 쌓아 둘 이유가 없다 — 오히려 산출물에 과거 버전까지 쌓이면 "지금 뭐가 최신인지" 헷갈리는 부작용이 생긴다.
- **Alternatives considered**: 산출물도 라운드별로 누적(계획 2단계 설계) — spec.md 최종 결정으로 기각됨. 산출물마다 `-2`, `-3` 스냅샷 파일 생성(계획 1단계 설계) — 마찬가지로 기각됨. 두 경우 모두 "산출물=최신 상태 하나, 이력=로그"라는 최종 역할 분리와 맞지 않는다.

## Decision: 인용 시 선별적 스테이징 — 대상은 로그 파일뿐

- **Decision**: 어떤 작업이 `.zenuml/log/<slug>.md`를 실제로 읽고 근거로 인용하기로 결정한 순간, `git add -f <그 로그 파일 경로>`로 그 파일 하나만 강제 스테이징한다. 다이어그램 산출물(`.zenuml/<slug>.md`)은 재생성마다 교체되어 이력으로서 가치가 없으므로 이 컨벤션의 대상이 아니다. 이 컨벤션은 `SKILL.md`(이미 버전관리 대상)에 절로 문서화하며, 다른 Spec Kit 스킬 파일은 수정하지 않는다.
- **Rationale**: spec.md FR-007이 "로그 파일"만 인용 대상으로 명시한다. `.zenuml/`은 이미 gitignore 대상이므로 일반 `git add`로는 스테이징되지 않는다 — 이를 우회하는 표준적이고 유일하게 간단한 방법이 `git add -f`다. 별도 `.gitignore` negation 패턴은 상위 디렉토리가 무시되면 대부분 적용되지 않는 알려진 제약이 있어 채택하지 않는다.
- **Alternatives considered**: 산출물 파일도 함께 스테이징 대상에 포함 — 산출물은 이력이 아니라 "현재 상태"일 뿐이라 인용 근거로서의 가치가 로그보다 낮고, spec.md도 로그 파일만 언급하므로 범위를 넓히지 않는다.

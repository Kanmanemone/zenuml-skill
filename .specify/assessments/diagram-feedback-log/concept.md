# Concept: 다이어그램별 개선 이력 로깅 + 후속 Spec Kit 개선 파이프라인

- **Slug**: diagram-feedback-log
- **Created**: 2026-07-28
- **Recommended option**: Option A — 최소 로깅 (AskUserQuestion 재활용 + 선별적 스테이징)

## Options

### Option A — 최소 로깅 (AskUserQuestion 재활용 + 선별적 스테이징)

- **Sketch**: `generating-zenuml-diagrams`가 다이어그램을 제시한 직후, AskUserQuestion을 다시 사용하되 "Other" 자동 자유 텍스트를 개선점 입력 필드로 활용한다: 질문 문구 자체에 hint를 담아("고치고 싶은 점이 있다면 적어주세요 — 없으면 아래에서 골라주세요"), 라벨 옵션 두 개는 [아무것도 안 함](순수 스킵 버튼)과 [사유 없이 다시 생성](구체적 피드백 없이 그냥 재시도)으로 채운다. 사용자가 구체적 개선점이 있으면 두 라벨 중 아무것도 고르지 않고 자동 제공되는 자유 텍스트("Other")에 바로 타이핑해 제출한다 — 별도 후속 질문 없이 한 번의 상호작용으로 끝난다. "아무것도 안 함"을 고르면 아주 짧고 고정된 응답만 오가므로 토큰 소비가 사실상 0에 가깝다(왕복 자체가 있는 한 완전히 0은 아니다). 사이클(최초 요청·최초 결과 링크·개선점·재생성 결과 링크)은 다이어그램 하나당 파일 하나에 이어붙이고, 여러 라운드가 이어지면 같은 파일에 계속 누적한다. 요약·분석·자동 패턴 탐지는 하지 않는다 — 사람이 나중에 디렉토리를 직접 훑어보고 재료를 스스로 고른다.
  로그 파일은 기본적으로 버전관리 대상이 아니다(`.zenuml/`처럼 gitignore). 다만 향후 어떤 Spec Kit 실행이 로그 항목 하나를 실제로 인용/참조하는 순간, 그 항목 하나만 그 자리에서 git stage에 올린다 — 로그 전체를 미리 커밋해두는 것이 아니라, "언급된 것만 선별적으로 버전관리에 편입"하는 지연(lazy) 방식이다.
  - **경위 — 왜 다시 AskUserQuestion인가**: 이전 개정에서는 "첫 번째 선택지 자체가 텍스트 필드"라는 문자 그대로의 설계가 스키마상(라벨 옵션은 텍스트를 못 받음, 최소 2개 강제) 불가능하다고 보고 AskUserQuestion을 통째로 버리고 평범한 채팅 질문으로 대체했다. 그러나 도구가 자동으로 붙이는 "Other"가 이미 자유 텍스트 입력 필드 역할을 하므로, 그 문자 그대로의 설계만 불가능할 뿐 "한 번의 상호작용으로 스킵 또는 자유 입력을 고른다"는 **기능적 목표는 AskUserQuestion으로도 달성 가능**하다는 점이 이번에 확인됐다. 이 구조로 되돌리면 평범한 채팅 질문 방식이 새로 만들었던 위험(아래 참고)도 함께 제거된다.
  - **선택지 순서 통제 범위(확인됨)**: 우리가 정의하는 라벨 옵션들의 순서는 통제 가능하다(배열에 적은 순서가 그대로 반영됨). 그러나 "Other"는 이 옵션 배열에 속하지 않고 도구/UI가 자동으로 붙이는 요소라, 위치를 지정하는 파라미터 자체가 없다 — "Other를 맨 앞에 오게 하기"는 불가능하다. 따라서 hint는 옵션 순서가 아니라 질문 문구 자체에 담는 것으로 확정한다(위 Sketch 참고).
- **Appetite**: small (수일)
- **Trade-offs**: problem.md의 핵심 목표를 충족시키는 최소 단위이며, 구조화된 선택 UI 덕에 "아무것도 안 함" 경로가 짧고 예측 가능한 고정 payload로 끝나 토큰 비용이 낮고, 스킵 여부를 자연어로 해석할 필요가 없어 오판 위험도 없다. 대가는, 라벨 옵션이 최소 2개 강제되므로 "사유 없이 다시 생성"이라는 다소 인위적인 두 번째 선택지를 늘 함께 보여줘야 한다는 점(사용자가 원했던 순수 2択 화면과 100% 동일하지는 않음)과, 자동 요약이나 다중 스킬 일반화가 없어 로그가 쌓여도 패턴 발견은 사람 눈에 의존한다는 점이다. 선별적 스테이징 방식은 "인용된 것만 버전관리"라는 원칙에 깔끔히 들어맞지만, 인용되지 않은 로그는 로컬에만 존재하는 미버전관리 파일로 남으므로 기기를 옮기거나 실수로 지우면 그 이력이 통째로 사라질 수 있다는 대가가 있다.
- **Rabbit holes**:
  - **"언급" 감지를 무엇이 트리거하는가**: 에이전트가 어떤 Spec Kit 산출물을 쓰다가 로그 항목을 실제로 읽고 인용하기로 "결정"한 그 순간에 맞춰 그 파일 하나만 `git add`하는 결정론적 방식이어야 한다. 반대로 매 Spec Kit 실행마다 전체 로그 디렉토리를 다시 훑어 "언급 여부"를 판별하려 들면(아래 "토큰 소비" 참고) 설계가 쉽게 부풀 수 있다.
  - 라운드가 이어질 때 파일을 어떻게 갱신할지(덮어쓰기 vs append), 정확한 로그 디렉토리 이름/위치 — problem.md Open Questions에서 이어지는 미결정 지점.
  - 두 번째 라벨("사유 없이 다시 생성")의 정확한 문구와, 그것이 실제로 선택됐을 때 로그에 무엇을 기록할지(개선점 텍스트가 없는 재생성 사이클을 어떻게 표현할지)는 specify 단계에서 확정해야 한다.

### Option B — 범용 재사용 가능한 피드백 파이프라인

- **Sketch**: Option A의 로깅 메커니즘을 `generating-zenuml-diagrams` 하나에 묶지 않고, 저장소 내 다른 미래 스킬도 갖다 쓸 수 있는 공통 패턴(예: 공유 스니펫/서브스킬)으로 설계한다. 로그 항목에 명시적 스키마(어떤 스킬·다이어그램·라운드 수·"feature X에 의해 소비됨" 상태 등)를 부여하고, 항목이 소비되면 상태를 표시해 재사용 여부를 추적한다.
- **Appetite**: medium (수 주)
- **Trade-offs**: 나중에 다른 스킬이 생겼을 때 같은 인프라를 재사용할 수 있다는 것이 이론적 이점이지만, research.md가 명시한 대로 확인된 사용자는 1인뿐이고 이 메커니즘 자체가 아직 한 번도 실사용으로 검증되지 않았다. 아직 존재하지도 않는 미래 스킬을 위해 인터페이스를 설계하는 것은 investigate 단계에서 이미 지적된 "표본 1인의 메타 인프라 투자" 위험을 그대로 재현한다.
- **Rabbit holes**: "일반 패턴"이 되려면 스킬마다 다른 입력/출력 형태를 어떻게 추상화할지 정해야 하는데, 지금은 대상 스킬이 하나뿐이라 그 추상화가 맞는지 검증할 방법이 없다. "소비 상태 추적"을 만들다 보면 자연히 소비 여부를 판단하는 로직/도구까지 손대게 되어 problem.md가 명시적으로 비목표로 둔 "자동 패턴 탐지·요약 도구" 영역을 침범하기 쉽다.

### Option C — 지금은 만들지 않는다 (수동 메모로 대체)

- **Sketch**: 전용 인프라를 만들지 않고, 사용자가 재생성을 요청할 때 정말 유용한 교훈이라고 느끼면 그때그때 수동으로 스크래치 메모에 남겨둔다. `generating-zenuml-diagrams`를 실제로 몇 차례 더 써보며 재생성이 얼마나 자주 발생하는지 감을 잡은 뒤, 그 실측 근거를 가지고 이 아이디어를 다시 꺼낸다.
- **Appetite**: 없음 (엔지니어링 작업 자체가 없음)
- **Trade-offs**: research.md가 지적한 위험(표본 1인, 미검증 빈도, "패턴이 보인다"는 판단 기준 미정의, 로깅 자체가 새로운 잡무가 될 역설)을 전부 회피한다. 반면 problem.md의 Cost of Inaction이 그대로 실현된다 — 1원칙 위반이 계속되고, feature 001의 decision.md가 남긴 "정적 체크리스트로 충분한가"라는 질문은 여전히 답을 얻지 못한다.
- **Rabbit holes**: 없음(만들 게 없으므로) — 다만 "나중에 다시 꺼낸다"는 계획이 실제로 지켜지지 않고 무기한 방치될 위험이 유일한 리스크다.

## Recommendation

**Option A**를 추천한다. problem.md의 목표(교정 이력 보존, 선별적 재료화, Spec Kit 게이팅)를 충족시키는 데 필요한 최소 단위이면서, research.md가 강하게 경고한 YAGNI/조기 인프라 위험(Option B가 정확히 그 위험을 재현)은 피한다. 동시에 Option C처럼 아무것도 하지 않아 1원칙 위반과 미해결 질문을 방치하지도 않는다. Option B(일반화·자동 소비 추적)는 Option A가 실사용에서 실제로 쌓이고 쓰이는 것이 확인된 뒤에 다시 검토할 후보로 남겨둔다.

### 토큰 소비 우려에 대한 개념 수준 점검

사용자가 우려한 지점: "`.specify` 내에서 언급되면 바로 stage에 올린다"는 방식이 LLM 토큰 소비를 과도하게 늘리지 않을까. 개념 수준에서 보면 위험은 **구현 방식에 따라 갈린다**:

- **저위험 경로**: "언급"이 에이전트가 이미 그 로그 항목을 자료로 읽고 인용하기로 결정한 순간에 결부된다면(즉 Option A의 "선별적 소비"라는 목표 자체가 원래도 그 파일을 읽어야 하는 상황), 그 뒤에 `git add <해당 파일>`을 실행하는 것은 git 명령 하나일 뿐 추가 LLM 토큰을 거의 소모하지 않는다. 읽기 비용은 어차피 재료로 쓰기 위해 지불해야 했던 비용과 같다.
- **고위험 경로**: 만약 "언급 여부"를 판별하기 위해 매 Spec Kit 실행마다 로그 디렉토리 전체 내용을 에이전트 컨텍스트로 불러들여 대조한다면, 로그가 쌓일수록 그 스캔 비용이 선형적으로 늘어난다. 다만 이런 대조는 굳이 LLM이 할 필요가 없는 기계적 작업(파일명/슬러그 문자열 검색)이라 `grep` 같은 도구로 결정론적으로 처리하면 이 위험도 크게 줄어든다.

즉 "선별적 스테이징" 자체가 본질적으로 비싼 것은 아니며, **"무엇이 언급을 트리거하는가"를 사람이 판단·인용하는 행위에 결부시키고, 자동 대조가 필요하다면 LLM이 아닌 결정론적 도구(grep 등)로 처리한다**는 원칙만 지키면 토큰 비용은 기존의 "선별적으로 재료를 읽는다"는 목표 이상으로 늘지 않는다. 이 원칙을 지키는 구체적 메커니즘은 specify 단계에서 확정해야 한다(위 Option A Rabbit holes 참고).

## Out of Scope (for the recommended option)

- 로그 요약/분석 자동화, 패턴 자동 탐지 (problem.md Non-Goals에서 이어짐 — 사람이 직접 훑어본다)
- `generating-zenuml-diagrams` 외 스킬로의 일반화·공유 인터페이스 설계 (problem.md Non-Goals에서 이어짐)
- 팀/조직 단위 협업·거버넌스 (research.md, 확인된 사용자 1인)
- 기존 정적 자기검증 루프(AP-1~AP-5)의 대체·수정 (problem.md Non-Goals에서 이어짐 — 이 개념은 그 이후 국면을 다룬다)
- 로그 항목의 "소비됨" 상태를 자동으로 추적하는 기능 — 사람이 수동으로 판단·인용한다

## Assumptions to Validate

- AskUserQuestion의 자동 "Other" 필드를 개선점 입력 창으로 삼는 설계가 실제 렌더링에서도 사용자에게 "이게 자유 입력 자리구나"라고 자연스럽게 읽힌다 — 질문 문구의 hint만으로 충분한지, 아니면 옵션 설명에도 추가 안내가 필요한지는 specify 단계에서 실제 UI를 보고 검증 필요.
- 다이어그램 재생성 요청이 로그를 쌓을 만큼 실제로 자주 발생한다 — research.md Gaps에서 이미 "실측 근거 없음"으로 지적된 가정이며, Option A 채택 이후에도 여전히 검증되지 않은 채 남는다.
- 사람이 직접 로그 디렉토리를 훑어보는 것만으로 "패턴이 보인다"를 판단하기에 항목 수가 감당 가능한 범위에 머문다 — 항목이 지나치게 많아지면 Option A의 "요약 없음" 전제가 깨질 수 있다.
- "언급되면 스테이징"을 결정론적 트리거(에이전트의 실제 인용 행위, 또는 grep 같은 도구)로 구현할 수 있어 로그가 늘어나도 토큰 비용이 선형적으로 늘지 않는다 — 위 "토큰 소비 우려에 대한 개념 수준 점검" 참고, specify 단계에서 구체적 메커니즘 확정 필요.
- 인용되지 않은 채 로컬에만 남는 미버전관리 로그 항목이 유실되어도(기기 교체, 실수 등) 감내 가능한 손실이다 — 사용자가 명시적으로 "버전관리 대상 아님"을 선택했으므로, 이 손실 가능성은 트레이드오프로 받아들여진 것으로 간주한다.

# 문제 정의: 스크립트 기반 Markdown 다이어그램/PDF 변환

- **Slug**: exporting-markdown-diagrams
- **Created**: 2026-08-19
- **Inputs used**: intake.md, research.md

## Problem Statement

저장소 소유자가 이 프로젝트가 만들어내는 Markdown 파일로부터 오래 보관하거나 공유할 수 있는 산출물(이미지 또는 PDF) — Mermaid/ZenUML 다이어그램을 SVG/PNG로 export하거나, `.md` 파일 전체를 PDF로 export한 것 — 을 원할 때, 지금 유일한 방법은 매번 Claude Code 에이전트에게 처음부터 변환을 추론해서 해달라고 요청하는 것뿐이다. 이는 기계적으로 결정적인 작업이므로 LLM 추론으로 처리하면 토큰이 낭비되고, 매 요청이 그때그때 에이전트가 즉흥적으로 고른 방식으로 독립적으로 처리되기 때문에 요청마다 결과가 일관되지 않다. 이 패턴은 과거 여러 세션에 걸쳐 반복돼왔지만 확립된, 재사용 가능한 절차는 없다.

## Affected Users & Stakeholders

- **Users**: 저장소 소유자 — 이 요청을 한 유일한 사람이며, export가 필요할 때마다 토큰 비용과 결과 불일치를 직접 감내하는 사람이다. [NEEDS CLARIFICATION: 이 저장소를 함께 쓰며 export된 다이어그램/PDF를 마찬가지로 필요로 할 다른 협업자가 있는가?]
- **Stakeholders**: 저장소 소유자 — 이걸 만들 가치가 있는지 결정하는 입장에서. intake·research 어디에도 다른 이해관계자는 확인되지 않는다.

## Goals

- 변환 작업의 기계적인 부분에서 LLM 토큰 소모를 없앤다 — 변환 자체가 에이전트의 다이어그램/문서 내용 추론을 필요로 하지 않아야 한다.
- 같은 종류의 입력을 반복해서 변환할 때마다, 그 세션에서 에이전트가 우연히 택한 방식이 아니라 매번 동일하게 동작하게 한다.
- 실제로 제기된 두 가지 변환 필요를 모두 커버한다: (a) `.md` 파일에 임베드된 다이어그램 → SVG 또는 PNG, (b) `.md` 파일 전체 → PDF.

## Non-Goals

- 새 다이어그램 *내용*을 생성하는 것 — 이는 이미 이 저장소의 기존 `generating-zenuml-diagrams`, `generating-architecture-views` 스킬이 담당한다. 이 문제는 이미 만들어진 Markdown/다이어그램을 다른 파일 형식으로 바꾸는 것에만 관한 것이다.
- 일관된 결과를 얻기 위해 대화형/수동 단계(예: GUI에서 우클릭)가 필요하게 만드는 것 — 리서치에서 이미 수동으로 이 작업을 해주는 VS Code 확장 프로그램들을 찾았다. 여기서의 아픈 지점은 export 능력 자체의 부재가 아니라, 구체적으로 *스크립트로 실행 가능하고 에이전트에 의존하지 않는* 경로가 없다는 것이다.
- 다른 저장소·팀·사용자를 위해 이 문제를 푸는 것 — 기록된 유일한 수요 신호는 이 저장소 소유자 본인의 반복되는 필요뿐이다.

## Success Metrics

- 다이어그램이나 Markdown 파일을 목표 형식으로 변환하는 데 변환 단계 자체는 LLM 추론을 필요로 하지 않는다 (baseline: 오늘날은 이런 변환의 100%가 에이전트의 전체 추론을 거친다 — intake에 따르면 이것이 바로 여러 세션에 걸쳐 반복돼온 패턴이다).
- 같은 입력을 반복 변환하면 매번 같은 결과가 나온다 (baseline: 오늘날은 측정되지 않음 — 과거의 각 변환이 독립적으로 즉흥 처리됐으므로 이를 보장하는 메커니즘이 없다).
- 이 저장소가 실제로 만들어내는 주력 다이어그램 산출물 — `.zenuml/*.md`의 `zenuml` 플레이버 시퀀스 다이어그램 — 이 일반 Mermaid flowchart뿐 아니라 이것도 성공적으로 변환된다 (baseline: 리서치에 따르면 흔히 쓰는 도구에서 2023년 업스트림 수정 전까지는 아예 실패했으므로, 별도로 신경 쓰지 않으면 "그냥 될 것"이라고 가정할 수 없다).

## Cost of Inaction

아무것도 바뀌지 않으면, 앞으로도 다이어그램이나 문서를 export해야 할 때마다 계속 에이전트를 통해 즉흥적으로 처리하게 된다 — 같은 토큰 비용이 반복되고, 결과가 들쭉날쭉할 위험도 반복되며, 요청 사이에 방식이 누적되거나 개선되는 것도 전혀 없다. 매번 방법을 처음부터 다시 만들어내는 것이며, 이는 아이디어 발화자가 과거 여러 세션에 걸쳐 이미 "여러번" 반복됐다고 지적한 바로 그 패턴이다.
